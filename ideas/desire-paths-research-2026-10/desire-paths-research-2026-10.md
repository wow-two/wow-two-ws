# Pave the paths our products already wore

*Synthesised 2026-10-27 from the 11 lane notes in [`lanes/`](lanes/), two later ones on interaction timing and notifications, and three on icons. Each claim links its lane; external sources keep the lanes' URLs. "(inference)" marks reasoning the lanes did not source; "(secondhand)" or "(snippet)" marks claims the lanes saw only through a summary.*

The strongest desire paths for both SDKs are in our own code, not in the literature. The fe sdk (`0.0.33`) already exports nearly every shell part, yet **22 products hand-assemble the same `AppLayout` frame**. In the be sdk, **10 to 17 products hand-wire the same SQLite setup, connection-string lookup, cookie-accounts block and mediator interceptor trio** ([own-codebase](lanes/own-codebase.md), [be-sdk-own-codebase](lanes/be-sdk-own-codebase.md)). A second path is adoption lag. `AccountMenu`, region scroll restoration and `AddPeriodicJob` were all built from product copies, but old pins keep the copies alive, and both product templates still seed new ones. The literature supports paving the intent behind a path rather than ratifying the literal workaround, and it warns that paving can drop what the path did: Twitter's first official retweet lost the commentary users had been adding. It offers one published threshold: GOV.UK acts on similar findings from 4 or more services ([foundations](lanes/foundations.md), [detection](lanes/detection.md)). For the gallery, the fe sdk's undeployed `apps/atlas` is the seed. It already holds typed layout, pattern and screen content, a themed grey wireframe kit with one accented element, and the 424 typed playground fixtures, all running on live source ([own-docs-and-hosting](lanes/own-docs-and-hosting.md)). No mainstream design system uses "component lit, layout dimmed" imagery, so the card would set the gallery apart, but no usability evidence backs it ([reference-galleries](lanes/reference-galleries.md)). The lowest-risk build is a live stage with a muted theme, plus Playwright stills in both themes ([spotlight-cards](lanes/spotlight-cards.md)). Storybook has nothing to keep: the Vue package has zero stories, and none of eight Vue libraries' docs sites is a Storybook ([docs-tooling](lanes/docs-tooling.md)). Hosting is the real constraint: conventions keep library repos at `deploy: none`, and no product has yet shipped a static-only Wheelhouse deploy. Two later lanes test the developer's 2026-10-27 ideas on interaction timing and notifications, and their points form the new Interaction & notifications pool: committing on a completed click and undo-first hold up, press-to-open holds only for mouse pointers, and an undo that lives only in a timed toast fails WCAG 2.2.1 ([interaction-timing](lanes/interaction-timing.md), [notifications](lanes/notifications.md)). Three icon lanes answer the developer's icon questions of the same day, and their points form the Icons pool: stay on lucide, moving to `@lucide/vue`, with allowlisted supplements; drop the Font Awesome scrape, since Free already ships as CC BY 4.0 SVG and Pro's licence blocks a published SDK; and build animated state icons as a CSS layer first, with a narrow Opus 5.5 harness for brand marks, domain glyphs and transition recipes ([icons-own-codebase](lanes/icons-own-codebase.md), [icon-sets](lanes/icon-sets.md), [animated-icons](lanes/animated-icons.md)).

## Desire paths are evidence of constraint, not a specification

The term's history is murky. "Desire line" first appears as a transport-planning term for a straight line from origin to destination (a 1946 Portland survey is cited). The Bachelard attribution is a myth. The campus "wait a year, then pave" stories are mostly unsourced: Michigan State's is reported only secondhand, and nothing supports the Ohio State version ([Landscape Architecture](https://www.landscapearchitecture.org.uk/desire-lines-key-principle-landscape-architecture/), [UW-Madison News](https://news.wisc.edu/desire-paths-the-unofficial-footpaths-that-frustrate-captivate-campus-planners/)). The software cases that survive checking are Twitter's. Users invented the @reply, the hashtag, the retweet and the thread, and Twitter paved each one, from official replies on 2007-05-30 to native threads on 2017-12-12 ([TechCrunch 2009](https://techcrunch.com/2009/08/13/twitter-announces-a-retweeting-api), [TechCrunch 2017](https://techcrunch.com/2017/12/12/twitter-officially-launches-threads-a-new-feature-for-easily-writing-tweetstorms/)). The retweet is also the warning. **The first official version dropped the commentary users had been adding**, and that commentary returned only in April 2015 as "retweet with comment" ([Levy via 3 Quarks Daily](https://3quarksdaily.com/?p=31323)) ([foundations](lanes/foundations.md)).

"Pave the Cowpaths" is §2.4 of the W3C's 2007 HTML design principles. It is a permissive compatibility rule: when authors already widely use a practice, consider adopting it instead of forbidding it or inventing something new. Its only example is the harmless `<br/>` syntax ([W3C](https://www.w3.org/TR/html-design-principles/)). Lachlan Hunt argued on the mailing list at the time that it should mean designing for what authors are trying to do, not copying their markup ([public-html](https://lists.w3.org/Archives/Public/public-html/2007Aug/0435.html)). Michael Hammer's 1990 HBR article uses the same idiom for the opposite advice: "stop paving the cow paths" when the process itself is broken ([HBR PDF](https://folk.idi.ntnu.no/thomasos/paper/hammer_reengineering.pdf)). For an SDK, Hunt's reading is the useful one. The limits that matter:

- **Paths self-reinforce.** A trail forms after about fifteen traversals, and later walkers follow the visible route, so popularity is not preference ([99% Invisible](https://99percentinvisible.org/article/least-resistance-desire-paths-can-lead-better-design/)).
- **Telemetry shows survivors.** A path in usage data shows who succeeded under today's design, not who gave up (inference, by analogy to Wald's bomber armour).
- **Some paths dodge a control that costs too much.** Adams and Sasse traced password circumvention mostly to how the mechanisms were implemented ([CACM](https://cacm.acm.org/?p=5985), snippet).
- **Paved behaviour becomes contract.** Hyrum's Law: given enough users, every observable behaviour gets depended on ([hyrumslaw.com](https://www.hyrumslaw.com/)).

The foundations lane turns these limits into a three-way test. The test is inference, and the examples below come from our own code:

| Verdict | When | Our example |
|---|---|---|
| Pave the intent, keep what the path did | Frequent, harmless, a legitimate goal, a convention already shared | The hand-built frame in 22 products |
| Redirect: fix the cost, retire the workaround | The path dodges a control that costs too much | `aria-label` passed via `v-bind` because the SDK props types omit it |
| Leave unpaved | The path crosses a safety, data or convention line, or one product only | listing-shelf's eyebrow slot vs `ui-copy.md:12`; TNIS studio's 1,610-line re-skin |

**Thresholds are barely published.** GOV.UK usually investigates once it hears similar findings from 4 or more different services, and it waits for a clear body of evidence ([GOV.UK Design System](https://design-system.service.gov.uk/community/share-research-findings)). Figma's guidance is qualitative: a high detach rate is not always bad. athenahealth reviews detachments monthly against expected rates per component type and traces each one to a bug, a missing enhancement or an unexpected combination ([Figma, Design systems 104](https://www.figma.com/blog/design-systems-104-making-metrics-matter/)). Scaled to our ~30 apps, that suggests 3–4 distinct apps, counted as apps rather than raw hits (inference) ([detection](lanes/detection.md)).

**Detection on the developer side has to be built.** Teams elsewhere measure per-component override frequency (GitHub), overridden lint rules (Amplitude, Productboard) and design-system-vs-custom ratios ([Omlet blog](https://omlet.dev/blog/data-driven-design-systems-in-practice/), secondhand). The tools are React-only (react-scanner) or say nothing about Vue (Omlet, Radius Tracker). A `@vue/compiler-sfc` scanner is the realistic route, estimated at a day or two (inference). On the end-user side, the cheapest privacy-friendly stack is a first-party `track()` call plus self-hosted Plausible or Umami. Rage and dead clicks come from PostHog or Clarity: PostHog fires a rage click after three clicks within 30 px and 1 s each, but its self-hosting is "officially unsupported" ([PostHog autocapture](https://posthog.com/docs/product-analytics/autocapture.md), [PostHog self-host](https://posthog.com/docs/self-host)). The fe sdk's `analytics` module ships only console and memory providers ([own-docs-and-hosting](lanes/own-docs-and-hosting.md)).

The seed video, Kole Jain's "Why the best software must LIE to you" (2026-10-21), is about interaction timing and intent prediction, going by its chapters and cited sources. No transcript could be read, so nothing in this report rests on it ([YouTube](https://www.youtube.com/watch?v=S8DcTJm8pYM)).

## The fe sdk ships every shell part but no frame

The SDK exports `AppShell` and its regions, `PageHeader`, `Navbar`, `SidebarMenu`, `BottomNavMenu`, `AccountMenu`, `AppSwitcherMenu`, `CommandPaletteModal`, `DataRegion` and a toast bus. It also exports `createAppRouter`, which installs document titles and region-aware scroll restoration. What it lacks is the **assembly**: no part turns one list of destinations into a top bar plus a bottom bar, and none covers the session gate, the version badge, pre-paint theme plumbing or mutation feedback. The survey covered 35 apps in 30 repos, pinned between `0.0.24` and `0.0.33` ([own-codebase](lanes/own-codebase.md)).

- **The template seeds the drift.** The product template pins `0.0.24`, ships no frame, skips `createAppRouter` and hand-writes its header row (`GreetingPage.vue:16-22`). Sibling products contain byte-identical copies (`SignInScreen.css`, `FailureMessages.ts`), which points to copy-from-sibling; the copy direction was not proven.
- **The backlog misses the biggest paths.** The SDK backlog harvests product-reported gaps, Wheelhouse's above all (fe backlog `:126-160`). It has no row for the frame, the theme plugin or the mutation glue. Wheelhouse's own boundary line, "Shared capability gaps belong in the SDK. Product composition stays local.", files exactly these as composition.
- **Paving after the fact works.** `AccountMenu` was extracted from these menus, but most of the 14 hand-built menus sit on pins older than `0.0.28`.
- **Loading, error and empty states are the success case.** `DataRegion` appears in 77 files across 15 apps; only 7 apps still hand-roll loading triplets. Tables mostly use `DataTable`.
- **Some capability is ahead of demand.** One app has a command palette, one has breadcrumbs, none has shell-level recents, and only Haven uses the app switcher. None of these is a desire path yet.

The component-API lane explains why products route around the SDK and how libraries made that safe ([component-apis](lanes/component-apis.md)):

- **The ecosystem moved override points into the API.** Headless primitives replaced CSS-override fights; Headless UI's 2020 launch put a bullet-proof dropdown at 3–4 weeks of work ([Tailwind blog](https://tailwindcss.com/blog/headless-ui-unstyled-accessible-ui-components)). `asChild`, `class` passthrough with `tailwind-merge`, `data-state` attributes and composables followed. Each carries a cost. Primer removed `sx` for runtime cost, with a reported 55% faster server render (snippet) ([GitHub blog](https://github.blog/engineering/architecture-optimization/improving-site-performance-by-shipping-more-css/)).
- **A safe hatch has four parts.** A documented precedence ladder (Nuxt UI: defaults → app config → `UTheme` → `ui` prop → `class`), a merge helper, stable hooks (`data-*`, CSS variables) treated as semver surface, and library CSS in a cascade layer that loses to app CSS ([Nuxt UI](https://ui.nuxt.com/docs/getting-started/theme/components), [PrimeVue](https://primevue.dev/theming/styled/)). Treating the hooks as semver surface is inference.
- **Vue gives passthrough for free, until it doesn't.** Single-root components forward `class`, `style` and listeners automatically; multi-root components lose that silently. `defineModel` with a `default` can desynchronise parent and child ([Vue](https://vuejs.org/guide/components/attrs.html), [Vue v-model](https://vuejs.org/guide/components/v-model.html)).
- **Copy-paste ownership fits one app, not an SDK consumed by 30 repos.** shadcn's model removes overrides by moving source into the consumer (inference).
- **Contribution models need a parking place.** Brad Frost splits system components, product recipes and one-off snowflakes ([Frost](https://bradfrost.com/blog/post/design-system-components-recipes-and-snowflakes/)). GOV.UK boosts items that already exist in several departments' pattern libraries ([GOV.UK Design Notes](https://designnotes.blog.gov.uk/2022/09/07/how-we-prioritise-additions-to-the-gov-uk-design-system/)). Our equivalent is a repo-level grep, not a survey.

## App layouts: keep navigation static, shortcuts visible and undo cheap

The layout evidence is mostly NN/g and a few HCI lab studies, on content sites and small menus rather than SaaS suites. It still separates well-supported rules from vendor assertion ([app-layout](lanes/app-layout.md)):

| Rule | Evidence | Strength | Our products today |
|---|---|---|---|
| Keep desktop navigation visible | 179 participants: desktop nav use 27% hidden vs 48% visible; discoverability down more than 20% ([NN/g 2016](https://www.nngroup.com/articles/hamburger-menus/)) | Primary study | 22 apps: top bar plus phone bottom bar |
| Left rail with text labels for many or growing sections; 7–9+ items is fine | [NN/g 2021](https://www.nngroup.com/articles/vertical-nav/) | Primary guidance | Wheelhouse, listing-shelf |
| At most 4–5 visible items on phones | [NN/g 2015](https://www.nngroup.com/articles/mobile-navigation-patterns/); M3 via SAP | Primary + secondary | `BottomNavMenu` in 11 apps |
| Breadcrumbs only on deep hierarchies; costly on mobile | [NN/g 2018](https://www.nngroup.com/articles/breadcrumbs/) | Design reasoning | Wheelhouse `ScopeBar` only |
| A command palette is an accelerator, not primary navigation | [Superhuman 2021](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/) (vendor); GitHub's 2025 removal for "low usage", paused after pushback ([The Register](https://www.theregister.com/2025/07/22/github_command_palette_backtrack/)) | Weak; no usage study | museums-gallery only |
| Teach shortcuts at the moment of action; passive hint labels get ignored | [Grossman et al., CHI 2007](https://www.dgp.toronto.edu/~ravin/papers/chi2007_learninghotkeys.pdf); 853-person survey: discovery is mostly social (snippet) | Primary lab | transcript-forge's shortcuts modal |
| Undo over confirmation for reversible actions | [Raskin 2007](https://alistapart.com/article/neveruseawarning/); [NN/g 2015](https://www.nngroup.com/articles/user-mistakes/); Gmail Undo Send, 2009 | Opinion + guidance | `AlertModal` 7 apps, `ConfirmPopover` 5 |
| Static nav; personalisation user-set; adaptive ranking only in re-sorted lists | [Findlater & McGrenere 2004](https://www.cs.ubc.ca/labs/edapt/papers/findlater2004.pdf): adaptive slower than static, 15 of 27 preferred adaptable; [Findlater 2009](https://www.cs.ubc.ca/labs/edapt/papers/findlater2009.pdf); Office 2007 dropped adaptive menus (secondhand) | Primary lab | Wheelhouse's local `PinnedNav` |
| Users keep defaults, so the default experience matters most | [NN/g 2005](https://www.nngroup.com/articles/the-power-of-defaults/) | Primary, dated | — |
| An empty state shows status, teaches, and offers the next action | [NN/g 2021](https://www.nngroup.com/articles/empty-state-interface-design/) | Primary guidance | `EmptyState` in 14 apps |
| Drag-and-drop needs a keyboard path and a non-drag alternative | [NN/g 2020](https://www.nngroup.com/articles/drag-drop/) | Primary guidance | not surveyed |
| URL-encoded view state | Practitioner guides only | Weak | not surveyed |

NN/g's 2025 study replaces "novice vs expert" with three complex-app user types. Legacy users stick to defaults and build bookmark workarounds. Legends want shortcuts. Learners need inline help and templates ([NN/g](https://www.nngroup.com/articles/complex-apps-users/)). A portfolio of ~30 small apps, each used occasionally, leans Learner and Legacy (inference). Visible navigation, good empty states and discoverable time-savers therefore come before accelerators. The practical shell standard: a static rail or bar, user-set pins beside a separate recents list, and adaptive ranking only inside palette and search results, where position is never memorised.

The wiring lives in `HostConfiguration*.cs`, with a median of 238 lines (range 69–520) and a median of 41 calls, 16 of them SDK calls. The SDK spans 22 production areas: 151 sub-folders with code, 33 empty placeholders and 262 entry methods. Identity left core on 2026-10-27 for the `wow-two-sdk-beta.identity` domain repo ([be-sdk-own-codebase](lanes/be-sdk-own-codebase.md)).

- **Products override the same `AddApiDefaults` options.** Of the 29 that call it: `EnableOtlpExporters = false` 24 (+2 conditional), `SpaHosting` 25, `TrustProxiesFrom(Deployment)` 21, HTTPS redirection off in Development 20, `ValidatorAssemblies` 18, output cache off 18. Rate limiting off is only 9 → B2.
- **Haven shows where the SDK lacks a hook.** It carries five "Extraction candidate" remarks: a Postgres data-source and provider hook, cookie-carried JWT, service-to-service tokens, OpenAI and Anthropic providers (both SDK folders are empty), and an OTP store → B12.
- **Wheelhouse shows where an SDK default is wrong for us.** The SPA fallback reserves only `/api`. Wheelhouse also keeps its own connection-string key, migration version stamp and health predicate → B13.
- **One override is security-relevant.** TranscriptForge and Secrets Vault post-configure `ForwardedHeadersOptions` because the pinned SDK's proxy defaults could turn an untrusted `X-Forwarded-For` header into anonymous local access. Nobody checked whether current defaults still do this → B1.
- **Adoption lags behind extraction.** `AddPeriodicJob` was built from Wheelhouse's six near-copies and names seven consumer products, yet only Wheelhouse uses it. Two stale-pin products keep local `ToProblem` copies. Five products sit on pre-rename package IDs. The template pins `10.0.71-beta` and seeds the SQLite pair.
- **Some capability ships with no explicit user.** Comms (70 .cs), Tenancy, FeatureFlags, Localization, Captcha, Quotas and every Messaging broker have 0 products → B17.
- **The docs have drifted.** The README and `Meta.md` show the wrong namespace. The README and the registry name `AddMediator*Behavior` methods that do not exist. `package-registry.md` claims to be the single source of truth yet lags the code. 48 live sub-modules have no folder doc, including `Web/ExceptionHandling` (26 products) → B15, B16.

Other backend ecosystems paved the same kinds of paths with a default plus a documented way out ([be-sdk-galleries](lanes/be-sdk-galleries.md)):

- **Aspire's `AddServiceDefaults()`** wires OpenTelemetry, health checks and HttpClient resilience in one call. It enables OTLP exporters only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, the same gating 24 of our products hand-code ([Aspire](https://aspire.dev/get-started/csharp-service-defaults/)).
- **A default has to back off.** Spring's default beans step aside when the user defines their own (`@ConditionalOnMissingBean`), and Laravel's `mergeConfigFrom` lets users override only chosen keys ([Spring](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html), [Laravel](https://laravel.com/docs/12.x/packages)).
- **Compile-time guidance beats prose.** The `ASP0000` analyzer flags the `BuildServiceProvider` workaround ([ASP0000](https://learn.microsoft.com/en-us/aspnet/core/diagnostics/asp0000)). Options validation is lazy unless `ValidateOnStart()` is called ([Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options)); an earlier SDK self-measurement found 5 of 44 binding sites using it.
- **A module page template follows** (inference): the workaround it replaced → the default → the escape hatch → the documented cost.

No DOM hook names a component (`data-component` and `data-part`: 0 hits), although state attributes exist (`data-state` 80 times in 50 SFCs).
- **The be sdk** has a regular folder tree (`src/{Area}/{Module}/`) with `{folder}.md` docs for 103 of 151 live sub-modules. ### What the reference galleries teach

- **Component Gallery is the closest model.** It is a text-first index of 60 components, each with an "Also known as" alias list (Modal = Dialog, Popup), examples from 95 design systems, facet chips that carry counts, and an "Unmaintained" badge ([component.gallery](https://component.gallery/components/), [changelog](https://component.gallery/changelog/)) ([reference-galleries](lanes/reference-galleries.md)).
- **Mobbin's changelog is a list of search fixes.** It added synonym search (2023), fixed facets that dead-ended after a category was chosen (2025), and keeps filters when switching content type ([Mobbin changelog](https://mobbin.com/changelog.md)). Facets should be additive from day one.
- **Design systems agree on "when to use"; real rationale is rare.** GOV.UK's "Research on this component", M3's "Similar components" table and HIG's directive-then-reason bullets are the models ([GOV.UK](https://design-system.service.gov.uk/components/radios/), [M3](https://m3.material.io/components/dialogs/guidelines), [HIG](https://developer.apple.com/design/human-interface-guidelines/alerts)).
- **No mainstream system dims the layout around the featured component.** The nearest precedents are Primer's emphasised-part anatomy, HIG's sheet over a dimmed Notes document and M3's scrim. No page documents the desire path a component formalises, so that framing is original.
- **Doc sites fail in predictable ways:**
  - prose before examples;
  - stale screenshots;
  - components missing from the index;
  - dead-end facets;
  - name-only search;
  - an open-ended "Other" bucket;
  - no version shown.
- **Backend catalogues are generated from per-module metadata.** Aspire cards carry the icon, a one-line description, tag chips, an `aspire add` snippet, downloads and version; Quarkus adds a status badge and last-released date. The pages are generated from Quarkus metadata, Backstage `catalog-info.yaml` and the Spring Initializr JSON ([Aspire gallery](https://aspire.dev/integrations/gallery/), [Quarkus](https://quarkus.io/extensions/)). ### Rendering the spotlight without breaking the layout

- **Do not dim with `filter` or `opacity` on a container.** A child cannot opt out of its ancestor's compositing. The ancestor also becomes a stacking context and re-anchors `position: fixed` descendants ([MDN stacking context](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_positioned_layout/Understanding_z-index/Stacking_context), [Vue Teleport](https://vuejs.org/guide/built-ins/teleport.html)). Muting through custom properties has none of these side effects ([spotlight-cards](lanes/spotlight-cards.md)).
- **Teleported overlays leave the subtree.** Modals, menus and toasts render at `body`. They need a stage-owned teleport target, an inline demo, or an iframe like atlas's `FramePage`.
- **Our route needs no SDK change (inference, untested).** The stage carries a muted theme, and the wrapper around the target restores the real one, as `ThemeScope` already does for a subtree. The gallery-owned wrapper replaces the missing `data-component` hook.
- **Stills come from a dedicated generator.** Playwright locator screenshots, run under two `colorScheme` projects with animations disabled in a pinned Docker image, are encoded to lossless WebP (about 26% smaller than PNG) with content-hashed names ([Playwright](https://playwright.dev/docs/test-snapshots), [MDN image types](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types)). Reusing VRT baselines lets images lag within the 0.2 tolerance. Chromatic and Argos keep images behind their own UI, and Lost Pixel was archived on 2026-04-22.
- **Live cards cost runtime.** 100 cards of 20–40 components each is 2,000–4,000 live instances (estimate). Stills by default and a live stage on open is the safer mix; `content-visibility: auto` showed a 7x faster initial render in web.dev's demo ([web.dev](https://web.dev/articles/content-visibility)).
- **Accessibility is manageable.** WCAG 1.4.3 exempts a picture's dimmed context from contrast, but the focal component keeps normal contrast, hover motion respects `prefers-reduced-motion`, and the alt text names the component and its context ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)).

| Approach | Sync with code | Main risk |
|---|---|---|
| Live stage with muted theme (A) | Exact, always | Portals; runtime weight if every card is live |
| Playwright stills of A, light + dark (B) | Exact at generation time | Font and OS drift; churn without content-hash names |
| atlas wire kit as a second style (G) | Exact | Icons, images and third-party internals ignore tokens |
| VRT baselines reused as images (C) | Lags within tolerance | Platform-suffixed names, staleness |
| SVG via `dom-to-svg` or Satori (E, F) | Exact, or none for Satori | Maintenance uncertain; Satori cannot render Vue |

### Backend cards need a diagram, not a render

- **No diagram tool has a spotlight mode.** All of them use one model plus a style class on one element ([be-sdk-galleries](lanes/be-sdk-galleries.md)).
- **D2 fits best.** It writes each class into the SVG as a `class` attribute, so one exported diagram can highlight any module through CSS ([D2 classes](https://d2lang.com/tour/classes/)).
- **The alternatives cost more.** Mermaid injects its own `!important` styles, which makes after-the-fact CSS brittle ([Mermaid](https://mermaid.js.org/syntax/flowchart.html)). Structurizr needs one export per filtered view.
- **A container-level diagram is enough.** C4 says context and container diagrams suffice for most teams ([C4](https://c4model.com/diagrams)). So the backdrop is one "typical product" container view, drawn from the product template's five projects, with modules mapped onto containers or cross-cutting layers (inference).

## Storybook has nothing to keep; hosting is the real constraint

- **Our Vue package has no Storybook.** It has 0 `*.stories.*` files and no `.storybook/`, and its rules say executable demos live under `tests/` and `apps/playground/` (`FE/CLAUDE.md:17`). All 238 stories belong to the parked React package, which used to deploy Storybook, a showcase and a theme studio to GitHub Pages; `docs/ui-beta-roadmap.md:10` still links it ([own-docs-and-hosting](lanes/own-docs-and-hosting.md)).
- **Storybook supports Vue as a second tier.** Version 10.x runs Vue 3 through `@storybook/vue3-vite`, but Vue features trail React by one to three minor releases: CSF factories were React-only in 10.0 and reached Vue in 10.2 as a preview. Props and slots share one `args` object, an older friction point ([Storybook 10](https://storybook.js.org/blog/whats-new/storybook-10), [10.2](https://storybook.js.org/releases/10.2), [storybook#23470](https://redirect.github.com/storybookjs/storybook/issues/23470)) ([docs-tooling](lanes/docs-tooling.md)).
- **Vue libraries build their own docs apps.** Of the eight Vue libraries' docs sites inspected, none is a Storybook. Nuxt UI, PrimeVue and shadcn-vue use Nuxt; Reka UI and Element Plus use VitePress `1.6.x`; Vuetify and Naive UI run custom Vite apps; Ark UI uses Next.js and keeps a `.storybook` folder in its repo.
- **The test layer can move without Storybook.** Vitest browser mode with `vitest-browser-vue` (Vitest 4+) and `toMatchScreenshot` replaces story-driven tests ([Vitest](https://vitest.dev/guide/browser/visual-regression-testing)). Playwright's Vue component testing is still experimental. Running axe-core directly instead of through Storybook's addon is undocumented (inference).

Hosting is where the conventions push back ([own-docs-and-hosting](lanes/own-docs-and-hosting.md)):

- **Wheelhouse deploys products only.** A product needs a catalog entry with `deploy: wheelhouse`, a `deploy.yml` with sites and health-checked services, an environment-free Dockerfile and the marker workflow. Each `main` release goes to dev automatically and to prod by digest.
- **Nothing static-only has shipped yet.** The descriptor convention models an `edge` service with a `wget` health check, and Haven's `edge.Dockerfile` (a Node build stage, then `caddy:2-alpine`) is the nearest precedent. Haven itself has no `deploy.yml` yet.

The planned Docs site (#13, rated "Buy/wrap" with Starlight or Docusaurus) overlaps the gallery's purpose but sits far down that queue.
- **Feedback has nowhere to land yet.** The fe sdk's `/reporting` client needs an HTTP sink, and the Feedbacks app has not started, so a static gallery cannot collect feedback.

## Interaction timing and notifications

Two later lanes test the developer's ideas of 2026-10-27 against prior art and the fe sdk's code. The evidence backs the protective half of each idea: commit only on a completed click, prefer undo to routine confirmation, keep long work visible after the user leaves the page. It qualifies the rest. Press-to-open pays only for mouse pointers, an undo that lives only in a timed toast fails WCAG 2.2.1, and ordering a stack by remaining lifetime has no precedent. Three notification ideas (an expandable body, progress that follows the user off the page, lifetime order) exist in no web library, so they are design work rather than adoption ([interaction-timing](lanes/interaction-timing.md), [notifications](lanes/notifications.md)).

### Interaction timing: commit on release, open on press only for a mouse

- **Commit on a completed click is the standard.** WCAG 2.2 SC 2.5.2 Pointer Cancellation (Level A) calls up-event activation the most accessible way, because the user can still move away before releasing ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html)). Windows menu items commit as on button release ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/menurc/about-menus)), and Radix, Reka and Headless UI commit menu items on click or pointer-up.
- **Open on press is a mouse-only optimisation.** `pointerdown` fires before the browser knows a touch is a scroll ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event)), so touch press-open opens a menu mid-scroll. Reka issue 804 hit this on Select, and Radix behaves the same ([reka-ui#804](https://github.com/unovue/reka-ui/issues/804)). Radix Select, Headless UI's menu button and Reka Select therefore open on press for `pointerType === 'mouse'` only. The only figure for the gain is instant.page's ~80 ms (vendor claim) ([instant.page](https://instant.page/)).
- **Cost and reversibility do not decide it in practice.** Popover is cheap and reversible, yet it opens on click in every library read, and Radix DropdownMenu opens on press for every pointer type while Reka's opens on click. The common factor is emulating an OS menu (inference). Every press opener needs focus workarounds, and no W3C text says menu-open-on-down conforms to 2.5.2, so mouse-only gating plus easy dismissal is a defensible position, not a documented pass (inference).

| Open or commit | Radix | Reka (Vue) | Headless UI | Zag / Ark | Our SDK |
|---|---|---|---|---|---|
| Dropdown menu opens | Press, any pointer | Click | Press, mouse only | Click | Click |
| Select opens | Press for mouse, click for touch and pen | Press for mouse, pointer-up for touch | — | — | Click, via `PopoverTrigger` |
| Menubar opens | — | Press | — | — | Click |
| Popover opens | Click | Click | Click | Click | Click |
| Tabs activate | Mousedown | Mousedown | — | — | Click |
| Menu item commits | Click, or pointer-up after a press on the trigger | As Radix | Click, or quick release after 200 ms and 5 px | — | Click only |

A dash marks a trigger the lane did not read; source lines are in [interaction-timing](lanes/interaction-timing.md) §2 and §3.

- **Our SDK is click-only.** Its primitives are hand-made over `@floating-ui/vue`, not Reka or Radix. Every trigger opens on `click` (`DropdownMenuTrigger.vue:46-50`, `PopoverTrigger.vue:49-52`, `MenubarTrigger.vue:58`, `TabsGroupTab.vue:52-55`), and `pointerdown` serves only outside-dismiss, long-press, drag and gestures. It carries none of the press pitfalls, and it loses the ~80 ms and press-drag-release.
- **Submenus run on two fixed timers.** A submenu opens after a 100 ms rest (`MenuSubTrigger.vue:14`) and closes 250 ms after the pointer rests on another row (`Menu.vue:59`), with no direction check, so a diagonal move toward the submenu can still switch rows (inference from code). Radix and Reka ship a grace polygon toward the submenu, and Kamens' menu-aim delays a row switch only while the cursor heads for the submenu ([radix menu.tsx](https://github.com/radix-ui/primitives/blob/main/packages/react/menu/src/menu.tsx#L484-L492), [reka useGraceArea.ts](https://github.com/unovue/reka-ui/blob/v2/packages/core/src/shared/useGraceArea.ts#L6-L70), [jQuery-menu-aim](https://github.com/kamens/jQuery-menu-aim/blob/master/jquery.menu-aim.js)).
- **Press-drag-release needs press-open first.** Headless UI's quick release selects the item under the pointer only after a 200 ms hold and 5 px of movement, so a plain click never counts as a drag ([use-quick-release.ts](https://github.com/tailwindlabs/headlessui/blob/main/packages/@headlessui-react/src/hooks/use-quick-release.ts#L22-L113)). A menu that opens on release cannot be dragged into, and our `MenuItem.vue:158-163` listens to `click` only.
- **Prefetch is the zero-waste use of press.** It commits nothing. instant.page reports ~80 ms on `mousedown` and ~90 ms on `touchstart` with no unused requests (vendor claims), and SvelteKit's `tap` mode preloads on either ([SvelteKit](https://svelte.dev/docs/kit/link-options)). Our SDK warms route chunks and queries on hover and focus only (`UsePrefetch.ts`, `UsePrefetchQuery.ts:16-21`), which gives touch no warm-up.
- **Wait only when acting early would harm.** Raymond Chen's half-second double-click wait exists because a stray second click would land in a newly launched window ([The Old New Thing](https://devblogs.microsoft.com/oldnewthing/20090429-00/?p=18413)). Otherwise the lane orders the alternatives: make the first action a safe subset of the second, split click from drag by distance (5–10 px) rather than time, and arm a hold timer only when someone listens, as `Button.vue:373` already does (inference). The 300 ms mobile tap delay is gone for pages with `width=device-width` ([Chrome for Developers](https://developer.chrome.com/blog/300ms-tap-delay-gone-away)); our apps' viewport tags were not checked.
- **Kole Jain's channel is a pattern feed, not evidence.** The first page of its Videos tab lists about 30 videos since 2024-12, mostly design listicles with Figma files and sponsors that borrow patterns from named products such as Linear, Apple and Stripe. The seed video is the only one that cites engineering sources (Chen, Kamens), and no transcript of any video could be read. Its chapter titles still point at relevant work: toast notifications, delayed tooltips and progress bars in `ld1zhQMXxXU`, keyboard-first and drag and drop in `Vy0KKvZJRH8`, swipe in `14h1VnkQvIc` ([channel](https://www.youtube.com/@kolejain/videos)).

### Notifications: extend the host, and give undo a route that outlives the toast

The notification work extends a mature host; it is not a rewrite. `ToastHost` already pauses on hover and focus, keys durations by severity, runs promise toasts, de-duplicates by `key`, updates in place and shows a countdown, and `NotificationCenterGroup` renders the bus's retained history. No planning doc defines a notifications vector ([notifications](lanes/notifications.md)).

| Developer idea | Prior art | Our SDK today | Evidence |
|---|---|---|---|
| Undo replaces most confirms | Raskin 2007; NN/g 2015 still recommends confirming deletion but warns that frequent confirmations get clicked through ([app-layout](lanes/app-layout.md)) | `UndoBar`, beside `AlertModal` (7 apps) and `ConfirmPopover` (5) | Supports, for reversible actions |
| Extra content expands on hover or tap | None per toast; Sonner and Mantine expand the stack, and iOS expands a Live Activity on touch-and-hold (secondhand) | `Toast.vue` default slot takes content; no toggle | Novel; WCAG 1.4.13 shapes it |
| Action buttons under the message | Sonner, Radix (`altText` required), Zag; Carbon allows one action | `actions` slot under the body (`Toast.vue:134-136`) | Supports; built |
| Pinned status for long-running work | Platforms only: Windows updates by tag, Android, iOS Live Activities, Chrome's download bubble (secondhand); VS Code keeps progress in context first | Promise toast and retained list; nothing relocates | Supports; no web library does it |
| Durations by kind, undo longer | Type tables in Notivue, Zag and react-hot-toast, never keyed by undo; Gmail's undo window is 5, 10, 20 or 30 s | Default 5000, `danger` 8000, `UndoBar` 5000 | Supports; longer alone does not meet 2.2.1 |
| Short-lived above or under long-lived | None; Mantine, Zag and Fluent rank by explicit `priority`, and most put the newest at the edge | FIFO, oldest first (`ToastHost.vue:480`) | No precedent; would reshuffle as timers expire (inference) |
| Timers extend while hovered | Near-universal, in three variants: resume the remainder, restart (Mantine, probably), or a set time after interaction (MUI) | Stack-wide pause; the remainder resumes | Supports; built |

- **Undo has two surfaces and two mechanics.** `UndoBar` is a bottom-center snackbar outside the bus (`UndoBar.vue:42-47`), so an undo published through `notify` would land top-right in the toast stack instead. Deferred commit hides the item and runs the operation after the window, so Undo only cancels a timer, but the operation is lost if the page goes away, and MDN calls `beforeunload` unreliable on mobile ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)). Compensating action runs at once and Undo restores; it survives navigation and tab close but needs a restore path. No source compares their failure rates.
- **An undo that lives only in a timed toast fails WCAG 2.2.1.** The criterion applies when the user has no other route to the information or action. Pause on hover is not one of its three remedies (turn the limit off, adjust it over a tenfold range, or warn and extend), and Gmail's 5–30 s setting spans only 6x ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)). A non-timed route such as a history entry is the likely fix, and only compensating actions can offer it after the toast closes (inference). Whether an undo window is an essential limit is unsettled; the WAI-IG thread holds two messages ([WAI-IG](https://lists.w3.org/Archives/Public/w3c-wai-ig/2025AprJun/0078.html)).
- **"Costs something" has an evidence-shaped meaning.** Raskin's essay does not cover irreversible actions ([A List Apart](https://alistapart.com/article/neveruseawarning/)). The lanes' poor fits for undo are effects that leave the system during the window (sends, payments, webhooks), data that cannot be restored, and data others edit at the same time (inference, backed by a secondary decision-framework piece in [app-layout](lanes/app-layout.md)).
- **Pinned progress needs its own region and an owner that outlives the route.** VS Code keeps progress in context and calls a progress notification a last resort, the same order as the developer's in-page-first idea ([VS Code](https://code.visualstudio.com/api/ux-guidelines/notifications)). Atlassian forbids mixing dismissible and non-dismissible flags in one stack ([Atlassian](https://atlassian.design/components/flag/usage)). Windows replaces a progress notification at completion, because the user may have dismissed it and still want the outcome ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-progress-bar)). WCAG 2.2.2 (Level A) requires a pause, stop or hide control for auto-updating content beside other content, so the hide button is required ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)). The bus and `ToastHost` are module-level, so SPA route changes are easy, but `UploadQueue` cancels its remaining uploads on scope disposal, so a route-scoped queue dies on navigation; full page loads need persistence.
- **Durations cluster at 4–6 s.** 5 s is the most common floor, and Adobe Spectrum sets a 6 s accessibility minimum (Dialtone too, snippet). At Brysbaert's 238 words per minute (snippet), a 5–6 s floor covers roughly 20–24 words (inference). No source gives a usable reading-time formula: Spectrum's +1 s per 120 words adds far less time than measured reading speed needs (inference).
- **Basics most libraries ship are missing.** In the lane's 12-column matrix, pause on a hidden tab appears in 6 columns (plus 1 opt-in), swipe dismiss in 6, a hotkey to focus the region in 5 and per-type politeness in 3. Our host has none of them. It has no `visibilitychange` handling, and one polite `Announce` carries only the latest string title, so a VNode title announces nothing. EUI adds "Clear all" at 3 toasts; ours has `dismissAll` with no control.
- **Two unrelated functions share the name `notify`.** One is the in-app bus (`FeedbackBus.ts:285-287`, imported by 22 apps per [own-codebase](lanes/own-codebase.md)), the other the OS-notification wrapper (`Notify.ts:147`). New `FeedbackNotice` fields also do nothing until `toToastOptions` forwards them (`FeedbackToastHost.vue:23-32`), and it does not forward `category` today.
- **Gallery demos have no library model.** No library has a supported cell for an expandable body, cross-navigation progress or lifetime order, so no demo exists to copy (inference). The playground's `FeedbackExamples.ts` only smoke-renders the toast components, and toasts teleport to `body`, which puts their demos in an iframe like atlas's `FramePage` (G5).

## Icons

Three lanes test the developer's icon questions of 2026-10-27 against our code, the sets' licences and the prior art for animated icons. They answer all three the same way: keep lucide as the set, aim our own drawing at the few needs lucide cannot meet, and add motion as a small state layer rather than a new library ([icons-own-codebase](lanes/icons-own-codebase.md), [icon-sets](lanes/icon-sets.md), [animated-icons](lanes/animated-icons.md)).

- **Build a harness or stick to existing icons: the evidence qualifies the either-or, with existing icons as the base and a narrow harness beside them.** The SDK and its consumers use 343 distinct lucide glyphs, about 22% of the 1,540 installed, and no code comment asks for a missing icon. Where lucide falls short, teams drew three kinds of glyph by hand: product brand marks (11 `BrandMark.vue` files, 9 of them inline SVG), domain glyph families (the files domain's 28 file-kind glyphs, TNIS's map marks), and parametric or status glyphs. A harness that draws a whole set answers a breadth gap the code does not show; one aimed at those three needs and at transitions answers a real one. Material, Carbon, Atlassian, Primer and Polaris own their sets, but with brand teams and gated contribution, which the lane reads as a size effect, not as evidence against adopting a set (inference).
- **Scrape Font Awesome: the evidence contradicts the long-held plan on licence and on coverage.** Free already ships as SVG under CC BY 4.0 on npm, GitHub and Iconify, so nothing needs scraping and the duty is attribution. Pro forbids standalone copies for non-licensees, and its FAQ rules out direct inclusion in open-source projects, so an SDK published to npm cannot carry Pro SVGs. Scraping adds no right, and a private-only SDK would need a lawyer's read. On coverage, Free's 2,000 solid icons sit in lucide's range (1,919 today) and add 608 brand marks; Pro's 61,764 count styles and variants, not concepts. No lane ran our 343 names against either catalogue, but the gaps the code shows (our own product marks, domain families, state glyphs, consistency) are ones no catalogue fills. `icon-scraper-spec.md` (2026-04-12) is still an idea with nothing built, the October idea review dropped it (score 27, licence blocker), and it conflicts with three convention rules: one set, no pasted SVG, no name strings.
- **Animate icons between states: the evidence supports it for feedback and qualifies the rest, since the gain is on controls rather than layouts and the first version needs no LLM.** NN/g calls a pencil morphing into a disk clearer than an instant swap, and SF Symbols binds a small fixed vocabulary (replace, draw on and off, variable draw for progress) to a state value. The same NN/g article warns that motion distracts and that many animations compete for attention, no controlled study compares morphing with swapping, and the worthwhile set is small: action → loading → done or error, copy → copied, toggles and progress. "Level up our layouts" therefore has no direct support; the sources describe clearer feedback on controls (inference). The layer is CSS over lucide. The Opus 5.5 harness comes second and writes recipes and missing glyphs under deterministic checks. No icon or animation benchmark includes Opus 5.5 (Claude Sonnet 4.5, measured on static SVG only, is the latest Claude), so a pilot has to settle its quality.

What the code shows beyond coverage ([icons-own-codebase](lanes/icons-own-codebase.md)):

- **The drift sits in rules that need a choice at each call site.** The rules that lucide or Tailwind enforce hold: one set, the default stroke (5 overrides on lucide tags), token colours. The rest drift. About 30% of `size` values fall off the 12/14/16/20/24 scale (15 ×123, 18 ×44 and 13 ×32 in consumers). Consumers use `SeverityIcons` 0 times and import 8 severity-like glyphs instead, labelled `<Icon aria-label>` appears 0 times, and refresh spreads over `RefreshCw`, `RotateCcw`, `Undo2` and `RotateCw`. 859 of 935 consumer glyph renders (92%) bypass the SDK `Icon`. Five components (`Alert`, `Toast`, `Callout`, `Banner`, `NotificationItem`) type `icon` as a string and render it as text, though no consumer passes one.
- **Lucide v1 forces a move whichever source wins.** npm marks `lucide-vue-next` deprecated in favour of `@lucide/vue`, which keeps the API, so the move is mostly find-and-replace. v1 removed 14 brand icons, Wheelhouse's `Github` among them, and hides icons from screen readers by default. We pin `0.460.0`, whose release date was not checked, while `@lucide/vue` reached 1.62.0 after 103 releases in a year, and 7 deprecated alias names are in use (`AlertTriangle`, `Loader2`, `Home` and others). The fe backlog row "Replace `lucide-vue-next`" (`:104`, Haven) records no reason ([icon-sets](lanes/icon-sets.md)).
- **No UI-icon drawing rules exist.** `conventions/design/` covers only product-identity icons (`identity/product-icons.md`), and the hand-drawn glyphs use strokes from 1.2 to 1.9 against lucide's 2. Lucide's published principles (24×24 canvas, 1px padding, 2px centred stroke, round joins, grid-snapped coordinates, reused base shapes) are a ready template, and they translate into lint rules.
- **Icon motion today is spinning only.** `Button` `isLoading` swaps the leading icon for a spinner in 168 uses across 26 roots, but `ButtonDataState` has no success or error state, and `CopyButton` swaps `Copy → Check → X` instantly. Apps rebuild state-to-icon maps (Wheelhouse's 10-state `StatusIcons`, ListingShelf's `FlowStateLook`). A library-wide CSS rule caps every animation under reduced motion, yet two spinners lack their own `motion-reduce:` class (the feedback `Spinner` and `SelectPicker`'s), and nobody checked in a browser whether the rule stops them.
- **Arcade uses emoji as UI marks.** It has no lucide dependency and draws close, back and forward, check and language marks as `✕`, `←` `→`, `✓` `✗` and `🌐`, which have lucide equivalents; nothing records why. Hijinx's emoji are mostly intended party-game tone.

The animated-icons lane's build, in order ([animated-icons](lanes/animated-icons.md)):

- **First, a declarative CSS layer over lucide.** Three API shapes exist: a state value that triggers the effect (SwiftUI), hover-triggered self-contained icons (lucide-animated: React and Motion, MIT, 350–470 icons, with a 39-star Vue port that has no releases), and imperative players (Lottie, Rive, GSAP timelines). The lane proposes the first for Vue: a `StateIcon` with a `state` prop and one lucide icon per state, an `AnimatedIcon` with an `effect` and a `trigger`, CSS keyframes keyed off `data-state`, and 6–10 named pair recipes (crossfade-scale, rotate, draw on and off through `pathLength`, shared-part replace, fill toggle, spin or pulse). Every transition starts and ends on the static icons, so SSR, the pre-hydration render and reduced motion all show a correct glyph (inference). A state change, not hover, is the default trigger. WCAG 2.3.3 (AAA) asks that interaction-triggered motion can be turned off; under reduced motion the state still switches, instantly or through a crossfade of 100 ms or less (inference).
- **Second, a harness that writes plans, not paths.** LLMs write transform, opacity and stroke-draw animation reliably but fail at non-rigid path deformation. In 2026 papers, frontier models failed about 12–14% of open-domain SVG animations, and rewriting whole documents made objects drift (VAnim, secondhand); no Claude model was evaluated. Lucide pairs also differ in topology: `play` is one polygon, `pause` two rects. So the LLM emits a plan per icon pair over persistent element ids (which elements stay, fade or draw), and the SDK compiles it to CSS. The checks are deterministic up to the last step: lint against lucide's rules and `svgo`, headless frames at 24 and 96 px, first and last frames pixel-matched against the static icons, a bounds check, a reduced-motion snap and a budget of about 300 ms. A contact sheet beside neighbouring icons then goes to a person for approval.
- **Skip true morphing and animation runtimes.** The lane rules out general path morphing, Lottie, Rive and Lordicon for product UI, Material's FILL axis (wrong set, font weight), model training, and Recraft or QuiverAI Arrow as the pipeline. GSAP's MorphSVG is now free under a non-OSI licence, for the rare pair that truly needs a morph, loaded lazily. The layer takes days and the harness 1–2 weeks, both lane estimates.

## Conclusion

The gallery is a detection instrument as much as documentation. A card that shows each product's pin next to its "used in" count makes adoption lag visible the moment an SDK part ships. A "ready, no product yet" state turns vector completeness into something the developer can review instead of a folder count. That loop matters more than any single paved API. The SDK backlog captures only what products report, and the largest duplications (the frame, the theme plugin, the mutation glue, the SQLite and cookie blocks) were never reported, because each product filed them as its own composition.

The cheapest paving is deletion. Region scroll restoration, document titles, `AccountMenu`, `AddPeriodicJob` and `ToProblem` already exist, so the first wins remove product code instead of adding SDK code. The second lever is the two product templates, which still seed the hand-wired frame and the SQLite pair into every new product. The gallery's own novelty has no precedent in the sources read: each item's philosophy page names the desire path it paves, and each card shows the component lit inside a dimmed layout. That is both an opening and a risk, so the card should be tested against a plain anatomy callout before the full set is built.
