# Backend SDK module galleries: catalogues, highlight-in-context diagrams, paved desire paths

Research date: 2026-10-27. Pages were fetched live that day; version/date facts are as the pages showed them. Where a fetch tool summarised a page rather than quoting it, the finding is phrased as the tool reported it. Opinion/philosophy pieces are marked **[opinion]**; secondary/blog sources are marked **[secondary]**.

## 1. How do backend ecosystems catalogue and present modules (taxonomy, card contents, filters, detail-page structure)?

### Takeaway
Every catalogue pairs a coarse category (sidebar/taxonomy) with free-form tags, and puts install command, version/status and a one-line description on the card. Detail pages are usually generated from per-module metadata (Quarkus extension metadata, Backstage `catalog-info.yaml`, Orchard `Manifest.cs`, Spring Initializr JSON), not hand-written. The richest "philosophy" content (why/when/what it replaces) is rare. ABP, Spring and NestJS put it in the guide docs, not on the card.

**NestJS (modules/recipes)**

**ASP.NET Core docs**
- The current APIs overview page is versioned across ASP.NET Core 6.0 to 12.0 monikers, with 10.0 the default. It says "For new projects, we recommend using Minimal APIs". — [ASP.NET Core APIs overview](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/apis)

### Inferences
- Two-axis structure is near-universal: one coarse category (Aspire 11, Quarkus 17, Orchard ~11, Spring 23 groups) plus free-form tags (Aspire chips, Backstage `tags`, Quarkus keywords). For ~20 modules, one category field plus tags is enough. A taxonomy of 8 to 12 categories would match the field.
- Status is a first-class badge only where lifecycles differ (Quarkus preview/experimental/deprecated, Backstage `lifecycle`). A beta-forever SDK could reuse the `experimental`/`production`/`deprecated` vocabulary, though "beta" may make `production` redundant.
- The card's most copied element is the install snippet (`aspire add`, `quarkus ext add`, Initializr "Add dependencies"). For this SDK the equivalent is the one-line `AddX()` call plus the `dotnet add package`.
- Detail-page sections converge on: what it is, install, configuration/options, UI (if any), events/telemetry, internals, related. ABP's Identity page is the closest template (Options, Distributed Events, Internals). None of the catalogues has a "why it exists / what workaround it replaces" section on the card or detail page. That would be a differentiator and matches the planned philosophy page.
- Generating the gallery from per-module metadata is the norm (Quarkus extension metadata, Backstage YAML, Orchard attributes, Initializr JSON). A single manifest per module (category, tags, status, summary, `AddX` signature, options type, dependencies) that drives both the gallery and the diagram would follow that precedent.
- Aspire's `Aspire.*` vs `CommunityToolkit.Aspire.*` split and ABP's Free/Pro tabs both separate "first-party" from "other". The planned gallery has only first-party modules, so a tier toggle is probably unnecessary.

### Gaps
- ASP.NET Core docs table-of-contents taxonomy (how the learn.microsoft.com TOC groups features) was not examined, only one overview page.
- `code.quarkus.io` selection UI (search, "Selected extensions", platform label) not readable; it is a JavaScript app.
- Orchard Core Features admin UI and `Manifest.cs` attribute reference were not read at primary source, only via search summaries.
- Laravel: no first-party package taxonomy found beyond the flat footer list; the docs sidebar "Packages" group was not captured.
- Backstage: the docs do not describe how the catalog UI renders cards and filters; only the data model was read.
- ABP: the module detail page on `abp.io/modules/...` (marketing page) was not read; only the docs page for Identity. Package-layer names (`.Domain`, `.Application`, `.HttpApi`, `.Web`) were not confirmed on the page read.
- Spring `start.spring.io` UI behaviour (search, "Add dependencies", EXPLORE/preview) was not examined, only the metadata JSON.

## 2. How do tools highlight one element in a dimmed system diagram, and which can be generated from code/config?

### Takeaway
No tool read has a built-in "spotlight this element, dim the rest" mode. The mechanism is always the same: one shared model, many views, plus a style rule keyed by tag/class that is applied to one element (Structurizr tag + `opacity`, D2 `class` / scenario with lower opacity, Mermaid `classDef` + `class`, IcePanel flow step highlight). All text-based options (Structurizr DSL, D2, Mermaid) are generatable from a manifest. The generating side must produce the model; none of the tools reads .NET code.

### Cited Findings

**C4 model**
- Four static levels (system context, container, component, code) and supporting diagrams (system landscape, dynamic, deployment). "You don't need to use all 4 levels": system context and container diagrams are enough for most teams. — [C4 diagrams](https://c4model.com/diagrams)
- C4 tooling page distinguishes diagramming tools ("boxes and lines", limited validation, no querying, copy-paste reuse, hard-to-diff files) from modelling tools (a non-visual model; diagrams are views; supports validation, renaming, querying, export). It recommends modelling tools, and lists diff-ability and git storage among the questions to ask. It does not cover auto-generation from code. — [C4 tooling](https://c4model.com/tooling)

**Structurizr (DSL, views, styles)**
- View types: `systemLandscape`, `systemContext`, `container`, `component`, `dynamic` (ordered relationship instances), `deployment`, `filtered` (by tag, from a base view), `custom`. If no views are defined a default set with auto-layout is created; defining any view removes the defaults. — [Structurizr DSL language reference](https://docs.structurizr.com/dsl/language)
- `include` / `exclude` take identifiers, expressions or `*`; including elements also brings in the relationships between them. `animation` steps reveal elements one step at a time. `autoLayout [tb|bt|lr|rl]`. — [Structurizr DSL language reference](https://docs.structurizr.com/dsl/language)
- Styles attach to tags (`styles { element "Tag" { ... } }`, with `light`/`dark` wrappers and `themes`). Element style properties include shape, icon, background, color, border, opacity. — [Structurizr DSL language reference](https://docs.structurizr.com/dsl/language)
- The reference documents no dedicated highlight feature. The fetch tool's own reading was that the closest mechanism is a unique tag plus an element style for that tag (tool inference, not a documented option). — [Structurizr DSL language reference](https://docs.structurizr.com/dsl/language)
- Export formats: PlantUML (`plantuml`, `plantuml/structurizr`, `plantuml/c4plantuml`), Mermaid, WebSequenceDiagrams (dynamic views only), static HTML site, PNG/SVG, JSON workspace/theme, plus custom Java exporters. D2 and DOT are not listed. CLI: `export -workspace workspace.dsl -format mermaid`, one file per view. Exports are generated from a workspace file (DSL/JSON), so diagrams stay in sync with that file. — [Structurizr export](https://docs.structurizr.com/export)

**IcePanel**
- Model/diagram split: objects and connections live in one shared model; adding an object to a diagram reuses it and edits apply everywhere; deleting from a diagram only removes the view. Levels follow C4 (context, apps, components); level 4 is replaced by linking objects to real code or infrastructure. Lower-level connections can show at higher levels and stay in sync. — [IcePanel diagramming](https://docs.icepanel.io/core-features/diagramming)
- Flows overlay a sequence of messages on an existing diagram and highlight the objects and connections in each step; the viewport re-centres per step; Back/Next, arrow keys; play vs edit mode (cmd/ctrl+E). Tags can be layered over a flow. Free plan: 3 flows per diagram. A search-tool summary found no dedicated "focus" mode beyond step highlighting. — [IcePanel flows (search results)](https://docs.icepanel.io/visual-storytelling/flows)
- "View dependencies" on an object's Connections tab shows incoming/outgoing dependencies; this is separate from flows. — [IcePanel diagramming](https://docs.icepanel.io/core-features/diagramming)

**D2**
- `classes` block defines reusable style sets; `class:` applies one; arrays apply left-to-right (later wins); an object's own attribute beats its class. Any class is written into the SVG as a `class` attribute, so post-export CSS/JS can target it. — [D2 classes](https://d2lang.com/tour/classes/)
- Composition: `layers` (new base, no inheritance), `scenarios` (build on the base), `steps` (build on the previous step). Boards are not visible simultaneously, so exports must represent them as dynamic diagrams (animated SVG in the page's example). — [D2 composition](https://d2lang.com/tour/composition/)
- Scenarios: each inherits from its base layer, can add objects and reference base objects to update them. The page's example scenario lowers the opacity of some objects and adds a connection ("Hotfix deployment" beside "Normal deployment"). — [D2 scenarios](https://d2lang.com/tour/scenarios/)
- Globs apply to existing and later-declared shapes; `*` targets shapes in the current scope, `**` recursive leaf shapes, `&` filters (AND), `!&` inverse filters, `***` across layers. Globs are described as a way to change theme defaults in one line. — [D2 globs](https://d2lang.com/tour/globs/)

**Mermaid**
- `classDef name fill:...,stroke:...;` defines a style; `class a,b name;` or inline `A:::name` assigns it; a class named `default` applies to nodes without a specific class. `linkStyle` targets links by 0-based definition order, so inserting a link shifts the target; edge IDs (`e1@-->`) avoid that. External CSS is unreliable because Mermaid injects its own styles with `!important`; `classDef` is the intended mechanism. — [Mermaid flowchart syntax](https://mermaid.js.org/syntax/flowchart.html)

**Backstage graph views**
- The catalog-graph plugin provides `EntityCatalogGraphCard` (entities directly related to the current entity, embeddable on the entity page, configurable relation filters) and a standalone `CatalogGraphPage` at `/catalog-graph`. `maxDepth`/`direction` options were not documented on the page read. — [Backstage catalog-graph plugin](https://github.com/backstage/backstage/tree/master/plugins/catalog-graph)

**Config-as-source-of-truth for architecture**
- Aspire's AppHost is described as "the code-defined source of truth for your architecture, including resources, references, and dependencies". — [What is Aspire](https://aspire.dev/get-started/what-is-aspire/)

### Inferences
- Simplest reproducible "dimmed diagram with one element lit" for a self-hosted gallery: one base diagram, one rendering per module where all other nodes get a `dim` class and the target gets a `lit` class. D2 exposes classes as SVG `class` attributes, so one exported SVG can be re-highlighted per module with CSS only, with no re-render. Mermaid's `classDef` can do the same per module at build time. Structurizr's `filtered` views and tag styles suit the C4 framing but produce one export per view.
- For an interactive gallery (card hover highlights the node), an SVG with stable per-node IDs/classes and CSS toggling is lighter than N pre-rendered images. This follows from D2's class-as-attribute behaviour and Mermaid's `!important` warning (post-hoc CSS is brittle in Mermaid, supported in D2).
- Generation path: a per-module manifest (id, category, depends-on, used-by-layer) can emit D2/Mermaid/Structurizr DSL text with a script. No tool read parses .NET code into a model; sync therefore depends on the manifest, not the compiler. The sync can be strengthened by building the manifest's `dependsOn` from `.csproj` project references (see section 3).
- C4's guidance that context + container diagrams are enough suggests the "typical product" diagram be a container-level view (host, web API, database, bus, storage, telemetry backend) and that modules map onto containers or onto cross-cutting layers drawn over them.
- IcePanel's "level 4 = link to real code/infrastructure" is a useful pattern for a card: the lit node links to the module's repo, package page and philosophy page.

### Gaps
- The exact D2 syntax for scenarios and for overriding a single node's style was not shown on the pages read (code samples did not render). Mermaid `style` per-node syntax also did not render.
- No source found for IcePanel API / Terraform / import-based sync with code. The page read did not cover it.
- Structurizr client libraries (Java/.NET) and component finders that extract components from code were not covered on the pages read.
- Whether Aspire can export its resource graph as a diagram (beyond the dashboard) was not verified.
- Backstage catalog-graph: `maxDepth`, `direction`, `unidirectional`, `mergeRelations` options not confirmed.
- Structurizr opacity-based "dimming" is stated only as a style property in the summary; a worked example was not read.

## 3. Where-used and dependency views: how catalogues show consumers, and how to compute it for our own repos

### Takeaway
Catalogues show where-used in two ways: declared relations (Backstage `dependsOn`/`dependencyOf`, derived read-only) and harvested dependents (NuGet "Used By", GitHub dependents). Both are limited: NuGet shows only the top 5 and only public data; GitHub needs a public repo and 100+ dependents for the sidebar. For a private ~20-product monorepo estate, the realistic source is the build graph (`dotnet package list --format json`, `dotnet nuget why`, `project.assets.json`) plus an optional Roslyn pass for `AddX()` call sites.

### Cited Findings

**How catalogues present where-used**
- Backstage relations are read-only and derived by processors from `spec` fields (`spec.owner` gives `ownedBy`/`ownerOf`; `spec.system` gives `partOf`/`hasPart`); descriptors should not include them, and consumers should prefer relations over raw spec. `dependsOn`/`dependencyOf`, `providesApis`/`consumesApis` exist on Component. — [Backstage descriptor format](https://backstage.io/docs/features/software-catalog/descriptor-format)
- NuGet.org "Used By" (announced August 2020) is the successor of "GitHub Usage" (2019). It lists the top 5 dependent NuGet packages (any version, latest stable of each dependent) alongside top GitHub repos. A full list was announced as a next step; whether it shipped was not confirmed in the sources found. — [NuGet blog: dependent packages](https://devblogs.microsoft.com/nuget/view-dependent-packages-on-nuget-org); [NuGet blog: GitHub usage](https://devblogs.microsoft.com/nuget/surfacing-github-usage-for-packages-on-nuget-org/)
- NuGet's design notes frame dependents as a trust signal for consumers and a success metric for authors. — [NuGet Home wiki: Used By](https://github.com/NuGet/Home/wiki/Showing-dependent-packages-on-NuGet.org-(Used-By))
- GitHub dependency graph: built from manifest and lock files plus the dependency submission API. The Dependents tab works for public repositories only. The "Used by" sidebar shows only if the graph is enabled, the repo publishes a package on a supported ecosystem, the package links to a public source repo, and more than 100 repositories depend on it. — [GitHub: about the dependency graph](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/about-the-dependency-graph)
- Aspire models consumption in the AppHost by "wiring resources to consuming projects with references" (environment variables / connection details), so the AppHost is a where-used record for resources. — [Aspire integrations overview](https://aspire.dev/integrations/overview/)
- Runtime introspection exists in other stacks. Spring's `ConditionEvaluationReportLoggingListener` prints which auto-configurations applied and why. Laravel packages add a section to `php artisan about` via `AboutCommand::add`. — [Spring Boot: creating auto-configuration](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html); [Laravel package development](https://laravel.com/docs/12.x/packages)

**Computing it for our repos (.NET tooling facts)**
- `dotnet package list` (noun-first form from .NET 10; `dotnet list package` on SDK 9 and earlier): lists top-level packages with Requested vs Resolved versions, `(A)` marks auto-referenced packages; `--include-transitive`; `--format json` and `--output-version 1` available from SDK 7.0.200; from .NET 10 it restores automatically (`--no-restore` to skip); `--outdated`, `--deprecated`, `--vulnerable` (SDK 9.0.300+). — [dotnet package list](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list)
- `dotnet nuget why [PROJECT|SOLUTION] PACKAGE [-f framework]`: shows the dependency graph paths for one package. It applies to the .NET 8.0.4xx SDK and later; 9.0.200+ produces separate trees per RID/framework; from the .NET 9 SDK it also accepts a `project.assets.json` (located via `msbuild -getProperty:ProjectAssetsFile`). — [dotnet nuget why](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-nuget-why)
- Roslyn: a `Compilation` is "analogous to a single project as seen by the compiler" (source files, references, options). `SemanticModel` is "the source for all the information you would normally get from intellisense". `GetSymbolInfo` binds names/expressions to `ISymbol`s, and `Kind`/`IMethodSymbol` let you inspect what a call refers to. Binding requires the right assembly references in the compilation. — [Roslyn semantic analysis](https://learn.microsoft.com/en-us/dotnet/csharp/roslyn-sdk/get-started/semantic-analysis)

### Inferences
- Three granularities for "used in": (a) package-level: product references `WoW2.Sdk.Beta.Be.X` (cheap, from `dotnet package list --format json` per product or a scan of `.csproj` / `project.assets.json`); (b) call-level: product actually calls `AddX()` (Roslyn: bind each `InvocationExpressionSyntax` with `GetSymbolInfo`, compare the `IMethodSymbol`'s containing assembly/namespace and name against the SDK's registration methods); (c) runtime: which modules a running service registers (a debug endpoint or startup log, analogous to Spring's condition report).
- (a) alone over-reports (a package may be referenced but unused), and transitive references via a meta-package would count every product as using everything. `dotnet nuget why` and `--include-transitive` distinguish direct from transitive.
- (b) is the only source that answers "which products really use the module". It needs a built `Compilation` (restored references). Loading via `MSBuildWorkspace` is a common route, though this was not verified in the sources read. A cheaper approximation is syntactic matching on method names, with false positives.
- Following Backstage's rule that relations are derived and never hand-written, the gallery's "used by" list should be generated into the manifest on CI and never edited by hand.
- NuGet/GitHub "Used By" are public-ecosystem features and add nothing for private products; do not plan around them.

### Gaps
- MSBuild's `-getItem` / `-getProperty` / `-getTargetResult` command-line switches (a lighter way than Roslyn to read `PackageReference`s) were not fetched, so they are unverified here.
- `MSBuildWorkspace` loading, `SymbolFinder.FindReferencesAsync`, and incremental-generator-based extraction were not covered by the sources read.
- GitHub dependency graph NuGet manifest support (`*.csproj`, `packages.lock.json`) was not confirmed on the page read.
- Whether NuGet "Used By" now has the promised full list: unverified.
- Cost/accuracy numbers for Roslyn analysis on a 20-product estate: no source.

## 4. Which backend API designs paved desire paths (workaround replaced, trade-off)?

### Takeaway
The recurring shape: the platform watched what people hand-rolled (temporary service providers, `/ping` endpoints, ad-hoc error JSON, startup threads, reflection-heavy registration), then shipped a default with an escape hatch. Each came with a documented cost: less extensibility (minimal APIs), hidden coupling (globals, `ServiceDefaults`), config-reload caveats (options), ordering fragility (Spring auto-config), or compile-time constraints (source generators).

### Cited Findings

**Minimal APIs, `WebApplication.CreateBuilder`, top-level statements**
- ASP.NET Core docs (page updated 2026-10-08) say "For new projects, we recommend using Minimal APIs" and list controllers as the alternative for: model-binding extensibility (`IModelBinder`/`IModelBinderProvider`), advanced validation (`IModelValidator`), application parts / application model, OData. They add that most of these "can be implemented in Minimal APIs with custom solutions, but controllers provide them out of the box". — [ASP.NET Core APIs overview](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/apis)
- The docs' stated benefits of minimal APIs: simpler syntax, better performance, easier testing, "modern approach". Hello-world is `WebApplication.Create(args)` + `MapGet` + `Run`. — [ASP.NET Core APIs overview](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/apis)
- David Fowler's "Minimal APIs at a glance" gist (.NET 6 era; says its content now also lives in the official docs) documents `WebApplication`/`WebApplicationBuilder`, handler forms, binding, `Results.*`, and escape hatches via `builder.Host`, `builder.WebHost`, `builder.Services`. At that release it lists missing MVC features (filters, model validation, form binding). — [Fowler: Minimal APIs at a glance](https://gist.github.com/davidfowl/ff1addd02d239d2d26f4648a06158727)
- **[secondary]** Motivation as retold by articles: controller-based Web API had "a bit of ceremony" for small APIs/microservices; the goal was less code to create HTTP endpoints. These are blog summaries; no first-hand quote from Damian Edwards or David Fowler was found. — [CODE Magazine: Minimal APIs in .NET 6](https://codemag.com/Article/2201081/Minimal-APIs-in-.NET-6)
- Worker/console hosts use `Host.CreateApplicationBuilder(args)` (`HostApplicationBuilder`) with the same builder shape. — [Worker Services](https://learn.microsoft.com/en-us/dotnet/core/extensions/workers)

**Options pattern**
- Purpose per docs: Interface Segregation (classes depend only on the settings they use) and Separation of Concerns; also validation. Rules: options class must be non-abstract with a public parameterless constructor; only public read-write properties bind (fields do not). — [Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options)
- `IOptions<T>`: singleton, no reload, no named options. `IOptionsSnapshot<T>`: scoped, recomputed per request, supports named options, cannot be injected into singletons. `IOptionsMonitor<T>`: singleton, change notifications and named options; change notifications only work for file-system based providers, and in Docker/network shares set `DOTNET_USE_POLLING_FILE_WATCHER=1` (poll every 4 s, not configurable). — [Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options)
- Library-author convenience: registering options of type `T` needs no explicit registration of `T`, so a library with simple defaults does not force the caller to pick a lifetime. — [Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options)
- Validation: `ValidateDataAnnotations()`, `Validate(...)`, `IValidateOptions<T>`; validation runs lazily unless `ValidateOnStart()` / `AddOptionsWithValidateOnStart<T>`; DataAnnotations do not recurse unless `[ValidateObjectMembers]` / `[ValidateEnumeratedItems]` are applied; a compile-time options validation source generator exists. — [Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options)
- `OptionsBuilder<T>.Configure<TDep1,...>` accepts up to five DI services so options can be configured from other services. The docs recommend a delegate over writing an `IConfigureOptions<T>` type. (Relevant to the `BuildServiceProvider` workaround below.) — [Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options)

**`IHostedService` / `BackgroundService`**
- Replaces the .NET Framework-era Windows Service model for long-running work; hosted services are "logging, configuration, and dependency-injection ready" and part of the generic host. `IHostedService` has `StartAsync`/`StopAsync`; `BackgroundService` adds `ExecuteAsync(CancellationToken)`; overrides of `StartAsync`/`StopAsync` must call and await the base method. — [Worker Services](https://learn.microsoft.com/en-us/dotnet/core/extensions/workers)
- Caveats: a run-once hosted service must call `IHostApplicationLifetime.StopApplication()` or the host runs forever; for short-lived jobs the docs suggest the generic host without a `Worker`. The Worker template does not enable Server GC by default (trade-off table given). User Secrets need an explicit package reference in the Worker template. — [Worker Services](https://learn.microsoft.com/en-us/dotnet/core/extensions/workers)

**ProblemDetails**
- `AddProblemDetails()` registers `IProblemDetailsService`; `CustomizeProblemDetails` decorates all generated responses; exception handler, status-code-pages and developer-exception-page middlewares then emit problem details (default `application/json`). `IExceptionHandler` handlers returning `true` must write the whole response (suggested: `IProblemDetailsService.TryWriteAsync`). `UseStatusCodePages` covers 4xx/5xx without a body. — [ASP.NET Core error handling](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling)
- Gotchas on the page: in API controllers `BadRequest()` writes first, so the auto-generated problem response is not replaced (use `ControllerBase.Problem(...)`). In .NET 10, diagnostics for handled exceptions are suppressed by default; in .NET 8 and 9 they were always emitted, so handled exceptions could be logged twice. The docs link RFC 7807 (not RFC 9457) and mention the third-party `Hellang.Middleware.ProblemDetails` as an alternative. — [ASP.NET Core error handling](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/error-handling)

**Health checks**
- `AddHealthChecks()` + `MapHealthChecks("/healthz")`; `IHealthCheck`; tags + `Predicate` select subsets; liveness (`Predicate = _ => false`) vs readiness (tagged `ready`); default status codes 200 for Healthy and Degraded, 503 for Unhealthy; responses are not cached by default; `IHealthCheckPublisher` for push monitoring. Warning: `Host` header filtering can be spoofed; mitigations are local port checks, host filtering, `RequireAuthorization`. `curl` is not in .NET Linux images, so a Docker `HEALTHCHECK` needs it installed. Community packages (`AspNetCore.Diagnostics.HealthChecks`) are not Microsoft-supported. The page does not discuss hand-rolled `/ping`. — [ASP.NET Core health checks](https://learn.microsoft.com/en-us/aspnet/core/host-and-deploy/health-checks)

**Aspire `ServiceDefaults`**
- A `YourApp.ServiceDefaults` library with one `Extensions.cs`: `AddServiceDefaults()` (entry point), `ConfigureOpenTelemetry` (logging, metrics for ASP.NET Core/HttpClient/runtime, tracing; OTLP exporters when `OTEL_EXPORTER_OTLP_ENDPOINT` is set), `AddDefaultHealthChecks` (a "self" check tagged `live`), `MapDefaultEndpoints` (`/health` all checks, `/alive` only `live`). `ConfigureHttpClientDefaults` applies the standard resilience handler and service discovery to every `HttpClient`. Marked `IsAspireSharedProject` so tooling references it automatically. — [Aspire service defaults](https://aspire.dev/get-started/csharp-service-defaults/)
- Customisation is by editing the generated source (uncomment Prometheus/Azure Monitor exporters, gRPC instrumentation, restrict discovery schemes). Guidance: keep the project to shared defaults; shared models belong in a normal library. For workers/WinForms without the ASP.NET Core framework reference, build a custom class library (example `AddAppDefaults`). — [Aspire service defaults](https://aspire.dev/get-started/csharp-service-defaults/)
- Trade-offs listed: health endpoints map only when `IsDevelopment()` (security note before enabling elsewhere); health-check traces are filtered out of tracing; resilience + discovery apply to every `HttpClient`; file-based AppHosts do not generate the project (`dotnet new aspire-servicedefaults`). — [Aspire service defaults](https://aspire.dev/get-started/csharp-service-defaults/)

**Source generators replacing reflection**
- Request Delegate Generator: compile-time source generator turning each `MapGet/MapPost/...` handler into a `RequestDelegate`; implicitly enabled for Native AOT or trimming, manually via `<EnableRequestDelegateGenerator>true</EnableRequestDelegateGenerator>`. Without it, delegates are built at runtime at startup. Benefits: AOT/trim-friendly, pre-generated delegates cut startup time. Constraints: JSON types must be on a `JsonSerializerContext` registered via DI; unsupported scenarios surface as build warnings, not errors; the docs mark Native AOT as preview for .NET 8 with partial feature support. — [Request Delegate Generator](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/aot/request-delegate-generator/rdg)
- `[LoggerMessage]` generator: partial methods; "eliminates boxing, temporary allocations, and copies to the maximum extent possible"; "Guided developer experience: the generator gives warnings to help developers do the right thing"; unlimited parameters vs a six-parameter cap in `LoggerMessage.Define`; dynamic log level supported; methods must be `partial`, `void`, and static ones need an `ILogger` parameter; supports redaction via data-classification attributes. — [Compile-time logging source generation](https://learn.microsoft.com/en-us/dotnet/core/extensions/logging/source-generation)
- The options page shows `[GeneratedRegex]` on a partial method inside an `IValidateOptions` implementation and links a compile-time options-validation generator. — [Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options)

**Analyzers steering people off a workaround**
- `ASP0000`: "Do not call `IServiceCollection.BuildServiceProvider` in `ConfigureServices`". Category Usage; the fix is non-breaking; reason: it creates a second copy of singleton services which can break behaviour; the page suggests injecting services as parameters to `Configure`. Listed for ASP.NET Core monikers 5.0 through 12.0. Suppression is advised only if removal is non-trivial and thoroughly tested. — [ASP0000](https://learn.microsoft.com/en-us/aspnet/core/diagnostics/asp0000)
- David Fowler's `AspNetCoreDiagnosticScenarios` repo collects "problematic application patterns for ASP.NET Core applications" with fixes: `AspNetCoreGuidance.md`, `AsyncGuidance.md`, `HttpClientGuidance.md`, `Gotchas.md`, a `Scenarios` folder (8.5k stars, 228 commits seen). The specific anti-patterns were not listed on the page. — [AspNetCoreDiagnosticScenarios](https://github.com/davidfowl/AspNetCoreDiagnosticScenarios)

**Spring Boot auto-configuration**
- Auto-configuration classes (`@AutoConfiguration`) load only from `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, must not be component-scanned, and back off with `@ConditionalOnMissingBean` when the user defines their own bean; `@ConditionalOnClass` activates by classpath presence. Replaces hand-written `@Configuration`/`@Bean` wiring and dependency/version alignment per library. — [Spring Boot: creating auto-configuration](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html)
- Documented trade-offs: bean conditions depend on registration order (reliable only on auto-configuration classes); `@ConditionalOnClass` on `@Bean` methods fails if the type is absent (needs nested config classes); referencing a bean in `@ConditionalOnExpression` initialises it early; splitting autoconfigure/starter adds maintenance; starters must balance opinionated defaults against optional dependencies. Testing uses `ApplicationContextRunner` (does not work in native images) with `FilteredClassLoader`. — [Spring Boot: creating auto-configuration](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html)

**Rails/Laravel conventions**
- **[opinion]** Rails Doctrine (DHH, undated, appears to be circa 2018 to 2019): Convention over Configuration (decide once, build deeper abstractions on conventions; DHH warns that deviating for minor reasons is often a mistake and the cost of going "off the Rails" is underappreciated), "The menu is omakase" (curated default stack; gives up some freedom), "No one paradigm" (admits "conceptual overhead"). — [The Rails Doctrine](https://rubyonrails.org/doctrine)
- Laravel package discovery installs service providers automatically via `composer.json`, with a consumer opt-out (`dont-discover`, `*` for all). Starter kits copy code into the app, so there is "no need to update the starter kit itself", the opposite of a versioned package. — [Laravel package development](https://laravel.com/docs/12.x/packages); [Laravel starter kits](https://laravel.com/docs/12.x/starter-kits)

**NestJS**
- Global modules reduce boilerplate but make dependencies implicit (docs discourage). Each extra `forRoot()` call creates another configured instance. — [NestJS modules](https://docs.nestjs.com/modules)

### Inferences
- Pattern for the philosophy page: each paved path has (workaround it replaced) → (default) → (escape hatch) → (documented cost). This section's entries fit that template, e.g. `BuildServiceProvider` temp-container → `OptionsBuilder.Configure<TDep>` / DI-aware registration → `IConfigureOptions<T>` → five-service cap and lifetime rules.
- Health checks, ProblemDetails, OpenTelemetry defaults and resilience are exactly the "every service rewrote this" set that Aspire `ServiceDefaults` bundles. A matching SDK module could be framed as "ServiceDefaults without the copy-paste": the SDK keeps the code, the product opts out per piece.
- Aspire's choice to generate `ServiceDefaults` as source in each solution gives easy customisation but means defaults drift per solution. A package-based module (the SDK's approach) updates centrally but needs explicit option hooks. This is an inference from the page's "uncomment options in Extensions.cs" guidance.
- `ValidateOnStart` plus `IValidateOptions` is the fail-fast option path; the docs show lazy validation by default, so an SDK that wants fail-fast has to opt in on each options registration.
- The catalogue of "which workaround each module replaces" can be seeded from this list: BuildServiceProvider, ad-hoc `/ping`, hand-rolled error JSON, `Task.Run` in startup, reflection-based endpoint registration, per-service OTel setup.
- Minimal APIs gained ground by being the documented default, not by making controllers go away: the docs keep a concrete list of what controllers still do better. An SDK module page can do the same ("when not to use").

### Gaps
- No first-hand statement from Damian Edwards or David Fowler on why minimal APIs / `WebApplicationBuilder` were created was found; only secondary summaries. The AspNetCoreDiagnosticScenarios contents were not read.
- Which .NET version introduced `AddProblemDetails`/`IProblemDetailsService`: not stated on the page read. RFC 9457 is not referenced by it.
- Rest of the long error-handling and health-check pages (past the first ~100k characters) was not read.
- OpenTelemetry defaults beyond what `ServiceDefaults` sets (semantic conventions, sampling) not researched. `Microsoft.Extensions.Options` configuration-binding source generator not fetched.
- Rails/Laravel conventions beyond the Rails Doctrine (e.g. Laravel facades, Eloquent conventions, `config/*.php`) were not researched; Rails Doctrine is a philosophy statement, not evidence of adoption.
- No independent evidence on how often developers hit each trade-off (e.g. IOptions reload surprises). Costs listed are documentation-stated.

## 5. Developer-experience principles for backend SDKs (one-line defaults with escape hatches, convention over configuration, discoverability, analyzers/code fixes)

### Takeaway
The frameworks read converge on four moves: a one-line entry point that picks sane defaults (`AddServiceDefaults()`, a Spring starter, `forRoot()`); a documented back-off or override for every default (`@ConditionalOnMissingBean`, `publishes` tags, `dont-discover`, `IConfigureOptions`); guidance delivered at compile time (`ASP0000`, RDG warnings, `[LoggerMessage]` diagnostics) rather than in prose; and metadata that makes the module discoverable (property docs, metadata JSON, `about` output, install snippets).

### Cited Findings
- **One-line default + customise by editing:** `builder.AddServiceDefaults()` wires OpenTelemetry, health checks, service discovery and HttpClient defaults; customisation is by editing the generated `Extensions.cs`, and the docs advise keeping that project to shared defaults only. — [Aspire service defaults](https://aspire.dev/get-started/csharp-service-defaults/)
- **Back-off as contract:** Spring Boot's default beans are skipped when the user defines their own (`@ConditionalOnMissingBean`); optional dependencies in the autoconfigure module make a missing library disable the config entirely. — [Spring Boot: creating auto-configuration](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html)
- **Property discoverability:** namespaced keys you own (`acme.*`, never `server`/`management`/`spring`), documented property descriptions with conventions, generated configuration metadata JSON for IDEs, and `Duration` types with units. — [Spring Boot: creating auto-configuration](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html)
- **Test the paved path:** Spring ships `ApplicationContextRunner` plus `FilteredClassLoader` to test "default backs off" and "ignored if library absent". — [Spring Boot: creating auto-configuration](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html)
- **Partial override instead of all-or-nothing:** Laravel `mergeConfigFrom` lets users override only chosen keys (first level only; nested arrays are not deep-merged); `publishes` with tags lets users publish just config, views or migrations; views resolve from the app's `vendor/{pkg}` folder first. — [Laravel package development](https://laravel.com/docs/12.x/packages)
- **Generated options + async twins:** NestJS `ConfigurableModuleBuilder` generates `register`/`registerAsync` (or `forRoot`/`forRootAsync`) and an options token, so authors do not hand-write the dynamic module boilerplate. — [NestJS dynamic modules](https://docs.nestjs.com/fundamentals/dynamic-modules)
- **Scaffolding as discoverability:** `nest g resource` generates the full file set and wires it in. — [NestJS CRUD generator](https://docs.nestjs.com/recipes/crud-generator)
- **Analyzers steer to the paved path:** `ASP0000` flags the `BuildServiceProvider` workaround; the `[LoggerMessage]` generator emits compile-time diagnostics "with hints about proper usage" and docs describe a "guided developer experience"; RDG emits build warnings for scenarios unsupported by Native AOT. — [ASP0000](https://learn.microsoft.com/en-us/aspnet/core/diagnostics/asp0000); [Compile-time logging source generation](https://learn.microsoft.com/en-us/dotnet/core/extensions/logging/source-generation); [Request Delegate Generator](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/aot/request-delegate-generator/rdg)
- **Fail early:** options `ValidateOnStart()` moves configuration errors from first use to startup. — [Options pattern](https://learn.microsoft.com/en-us/dotnet/core/extensions/options)
- **Ordering and lifecycle explicit:** ABP `[DependsOn]` plus Pre/Post configure phases give deterministic ordering; Orchard dependencies auto-enable (secondary source). — [ABP module basics](https://abp.io/docs/latest/framework/architecture/modularity/basics)
- **Encapsulation by default:** NestJS modules hide providers unless exported; the exports list is the public API. — [NestJS modules](https://docs.nestjs.com/modules)
- **Convention costs (opinion):** Rails Doctrine pairs "convention over configuration" with an admission that going off the conventions is costly and that the curated stack costs individual freedom. **[opinion]** — [The Rails Doctrine](https://rubyonrails.org/doctrine)
- **Package-level self-description:** Laravel packages can add their own version/info line to `php artisan about`. — [Laravel package development](https://laravel.com/docs/12.x/packages)

### Inferences
- A module's gallery entry could list "what you get by default" and "how to back off" as two explicit fields. This matches how Spring, Laravel and Aspire document modules, and it ties directly to the planned philosophy page.
- Where the SDK already has an analyzer or code fix for a module, naming it on the module page (rule ID, what it flags) would copy the `ASP0000` pattern of tying a workaround to its paved replacement. Whether the SDK ships such analyzers was not researched.
- The `ValidateOnStart` gap suggests every SDK options registration should enable fail-fast by default; this is an inference from the docs showing lazy validation as the baseline.
- Convention-over-configuration claims should be paired with the cost statement DHH makes: a module page that states "if you deviate from X, you lose Y" is more honest than one that lists only features.
- Property-doc conventions (Spring) translate to .NET as XML-doc comments on options properties and a generated options reference per module (the gallery could harvest those comments).

### Gaps
- "Pit of success" (Rico Mariani / Framework Design Guidelines) and other formal .NET API-design guidance were not fetched, so they are not cited here.
- No source read on analyzer/code-fix authoring practice (Roslyn analyzers with `DiagnosticDescriptor` help links, code-fix providers) or on how analyzers ship inside NuGet packages.
- No data on adoption of any of these principles (which ones developers actually follow).
- Conference talks (Fowler, Edwards, Aspire team) were not searched; blog posts by the maintainers were not retrieved.
- No source for DX measurement (time-to-first-run, support burden) for SDKs.
