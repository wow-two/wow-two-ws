# Open-source icon sets, licensing and delivery for a Vue 3 SDK (as of 2026-10-27)

Scope: sets, coverage and licensing only; animated icons and AI generation sit in a sibling lane. Not legal advice; points that need a lawyer are marked **[lawyer]**. Source tags: `primary` (licence file, vendor doc, registry/API), `secondary` (third-party write-up), `snippet` (search-result excerpt, page not read in full), `opinion` (practitioner/vendor blog), `own-measurement` (run in this session on 2026-10-27).

Retrieval notes: `fontawesome.com/license` and `/license/free` render client-side and returned only a page title to the fetch tool. The Free text was read from the official GitHub `LICENSE.txt`; the Pro licence and Pro FAQ were read through a text-reader proxy (`r.jina.ai`) of the official pages, so the quotes below are from fontawesome.com content but did not come through a direct fetch. ## 1. Licensing: Font Awesome Free vs Pro, scraping, and the other sets

### Takeaway
Font Awesome Free is already published as SVG under CC BY 4.0 (npm and GitHub), so nothing needs scraping; the obligation is attribution. Font Awesome Pro is a commercial licence that lets a seat-holder embed icons in their own websites and apps but bars "standalone copies" for non-licensees and, per the FAQ, direct inclusion in open-source projects; an npm-published SDK that carries Pro SVGs would redistribute them. Scraping creates no licence of its own: you inherit the terms of whatever you copy (plus any website terms), and the other sets are all permissive (MIT, ISC, Apache-2.0, CC0), with Remix Icon (custom licence since Jan 2026) the one to watch.

### Inferences
- "Scrape Font Awesome" has two readings. Free: unnecessary, since the same SVGs ship in `@fortawesome/free-solid-svg-icons` (12.1M downloads/month) and on GitHub under CC BY 4.0; the cost is a LICENSE/NOTICE entry plus keeping the file-header comments. Pro: the icons are only licensed to embed in the licensee's own Projects, so a public SDK that bundles Pro SVGs delivers "copies of Pro Icons ... for non-Creators" and "directly included in open source projects"; this reads as prohibited by the quoted text and the FAQ's own npm guidance is "bring your own token", not "bundle". **[lawyer]** for the exact boundary if the SDK is private/internal-only (35 own apps under one seat count may be fine) versus public on npm.
- Scraping itself adds no right: the copyright terms attach to the asset, and any website-terms or technical-access question is separate and unresolved here (ToS not read). A scraped copy of Pro assets has the same restrictions as a purchased one, with worse evidence of entitlement.
- CC BY 4.0 attribution can be met "in any reasonable manner"; in practice a `THIRD_PARTY_NOTICES` file plus preserved SVG header comments in the published package is the conservative route (opinion; not tested against a lawyer's read).
- The other candidate sets fit one policy: MIT/ISC/Apache-2.0/CC0 may be bundled with a retained notice; CC BY needs attribution; CC BY-SA, GPL and NC sets should be excluded from an allowlist. Remix Icon should be treated as custom-licence, not Apache-2.0, until its owner clarifies; its "competing icon library" clause is a direct risk if the SDK ever re-exports it as an icon set.
- Lucide's ISC licence carries an extra duty for the Feather-derived subset (MIT notice); the one list of those icons is on the licence page.

### Gaps
- Font Awesome website terms of service (scraping, automated access): not retrieved.
- Current Pro licence "Last updated" date and any 2025–2026 changes: not retrievable via the fetch tools; the 2018 copy matches the current wording on the points quoted.
- No primary statement from Font Awesome on whether embedding Pro icons in a closed-source, internally published component library (private registry) is a "Project". **[lawyer]** or ask FA support in writing.
- Per-set CC BY attribution wording for Solar/Streamline/other CC-BY sets not read.
- Whether "Embed" covers an SDK compiled into customers' apps (the 35 apps are the owner's own; third-party consumers of a public SDK are not).

## 2. Coverage and consistency: counts, styles, grid, cadence, Lucide's gaps

### Inferences
- If the SDK stays on Lucide, the highest-value, lowest-risk action is moving from deprecated `lucide-vue-next` to `@lucide/vue` (same API) and replacing the 14 removed brand icons; 3.66M vs 0.81M monthly downloads suggests most of the ecosystem has not moved yet.
- Visual match to Lucide ranks: Tabler (24×24, 2px stroke) is the closest in geometry; Heroicons (1.5px stroke) and Radix (15×15) differ; Phosphor "regular" and Material outlined differ in stroke/corner logic. Whether Tabler and Lucide look identical side by side was not tested.
- Neither Phosphor's nor Heroicons' npm packages shipped in 2025–2026, even though both repos show 2026 commits; for an SDK that wants an upstream that keeps adding icons, Lucide, Tabler, Simple Icons and Material Symbols are the evidently active ones.
- Only a use-case inventory (which icon names the 35 apps need) can answer "would Font Awesome cover all our use cases". Font Awesome Free's 2,000 solid icons are in the same range as Lucide's 1,919 and add 608 brand marks; Pro's 61,764 count includes styles/variants, not unique concepts.

### Gaps
- Domain-specific icon gaps in Lucide were not enumerated; needs the SDK's icon-name inventory against each set (a script comparing names/tags would answer it).
- Phosphor 2026 roadmap or a v3: none found; only a search-result README note that the legacy `phosphor-icons` package is replaced by `@phosphor-icons/web`.
- Stroke widths of Phosphor, Iconoir, Remix not verified from primary specs.
- Google's Material Symbols icon count is stated inconsistently on one page ("over 2,500 glyphs" vs "3,800+ icons").
- No evidence on "filled variants absent" from Lucide maintainers (a search of Lucide issues for "filled variant" returned nothing); inferred from the stroke-only design rules.

## 3. Aggregators: Iconify, @iconify/vue, unplugin-icons

### Takeaway
Iconify makes "scrape everything" unnecessary for every set licensed for redistribution: its API currently lists 244 sets and about 418k icons (docs say "over 300,000 ... 200+"), including FA Free but not FA Pro. `unplugin-icons` bundles only the icons actually used at build time; `@iconify/vue` fetches from the Iconify API at runtime unless icon data is added offline. Licence metadata is per set, not per icon, and the catalogue includes GPL and non-commercial sets, so an allowlist is needed.

### Cited Findings
- Counts: the official docs claim "over 300,000 icons from 200+ icon sets" ([@iconify/vue docs](https://iconify.design/docs/icon-components/vue/), primary); older pages say 200,000 and 150,000 ([getting started](https://iconify.design/getting-started), [docs.iconify.design/icons](https://docs.iconify.design/icons/), snippet); a January 2026 article says "over 275,000 icons from over 200 icon sets" ([Gigazine](https://gigazine.net/gsc_news/en/20260119-iconify-open-source-icons), secondary). My count of the live collections endpoint on 2026-10-27: 244 sets, 417,719 icons — [api.iconify.design/collections](https://api.iconify.design/collections) (own-measurement)
- Per-set metadata fields in `@iconify-json/lucide/info.json`: `name`, `total`, `author{name,url}`, `license{title,spdx,url}`, `samples`, `height`, `category` (e.g. "UI 24px"), `tags` (e.g. "Uses Stroke"), `palette`. `icons.json` keys are `prefix, icons, aliases, lastModified, width, height`; no per-icon licence or author field was found. — own-measurement on installed [@iconify-json/lucide](https://www.npmjs.com/package/@iconify-json/lucide) (primary data)
- Iconify categories include "Archive / Unmaintained" (the FA 6 sets) and "Logos" (Simple Icons, FA Brands), which can be used as filters. — [Iconify collections API](https://api.iconify.design/collections?prefixes=fa6-solid,simple-icons) (primary data)
- `@iconify/vue` 5.0.4 (2026-10-19), 3.42M downloads/month. Default behaviour: "No need to bundle icons, component will automatically load icon data for icons that you use from Iconify API." Offline: `addIcon()` / `addCollection()`; `setCustomIconLoader()`; `setFetch()`. The component "is not designed for server side rendering"; an `ssr` attribute (4.1.2+) renders immediately if data is available on both sides. The docs do not describe a switch to disable the API. — [@iconify/vue docs](https://iconify.design/docs/icon-components/vue/) (primary); [npm registry](https://registry.npmjs.org/@iconify%2Fvue) (primary)
- `unplugin-icons` 24.0.0 (2026-09-11; v23.0.1 and 23.0.0 2026-01-14; v22.5.0 2025-10-19), MIT, 1.88M downloads/month. Vue 3 via `compiler: 'vue3'`; import `~icons/{collection}/{icon}` as components; "Only bundle the icons you really use, while having all the options"; "Only icons you actually use will be bundled in production" when installing the full `@iconify/json` (about 120 MB) or individual `@iconify-json/*` packages; custom collections via `FileSystemIconLoader`, `ExternalPackageIconLoader`; ESM-only; Node 20+ since v24; Vapor needs `compiler: 'vue-vapor'` (otherwise "renders a virtual-DOM icon as nothing at all"); `autoInstall` is "Experimental"; the README says nothing about per-icon licensing (check each set). — [unplugin-icons README](https://github.com/unplugin/unplugin-icons) (primary); [GitHub API](https://api.github.com/repos/unplugin/unplugin-icons/releases) (primary)
- Nuxt UI's Vue integration: icons come from Iconify through `@iconify/vue`; Lucide is the default set; "Installing `@iconify-json/{collection_name}` lets the build embed the icons" so they render during SSR and work offline; otherwise icons "load from the Iconify API at runtime"; `icon.clientBundle.icons` or `clientBundle.scan` pre-bundle named icons. — [Nuxt UI icons docs](https://ui.nuxt.com/docs/getting-started/integrations/icons/vue) (primary)
- Font Awesome Pro is not in Iconify (only the Free subsets are: `fa7-solid` 2,000, `fa7-regular` 272, `fa7-brands` 608). — [Iconify API](https://api.iconify.design/collections?prefixes=fa7-solid,fa7-regular,fa7-brands) (primary data)
- Mixing sets: practitioner guidance is to pick one family, fix size/stroke/corner/detail rules before collecting icons, allow deliberate variation only inside one family (outline for rest, filled for active), normalise mixed sources to one grid, audit and record each icon's source. — [21st.dev](https://21st.dev/blog/react-icon-libraries), [freeicon.com](https://freeicon.com/blog/keep-icons-consistent-across-a-web-project) (opinion, vendor/agency content, snippet)

### Inferences
- A practical architecture is "one primary family + a small, named set of supplements": Lucide as the base, one same-geometry supplement (Tabler) for filled/extra concepts, Simple Icons for brands, and own SVGs in a custom collection. Iconify's `category` ("UI 24px") and `tags` metadata can drive an automated gate (grid, stroke-based, licence SPDX) so an unlisted set cannot enter by accident.
- A build-time pipeline (unplugin-icons, or a script that reads `@iconify-json/*` and emits per-icon Vue components) avoids runtime calls to `api.iconify.design`; the default `@iconify/vue` path adds a runtime third-party dependency and a privacy/offline question for 35 apps.
- Because licence metadata is per set, the allowlist needs to be per set and recorded in the SDK (a `icon-sources.json` with SPDX, version and notice text); Iconify does not track the duty for CC-BY attribution for you.
- For a published component SDK, the build-time plugin runs in the SDK's own build; consumers receive ordinary compiled components. Whether the plugin is needed at all (versus importing from `@lucide/vue` directly) depends on how many non-Lucide icons are pulled in. This was not tested end to end.

### Gaps
- Iconify's own documentation of licence handling (e.g. a statement on how it vets sets) was not read.
- No head-to-head benchmark found for `unplugin-icons` vs `@lucide/vue` bundle size (see Section 4 for own numbers for Lucide only).
- Precise count of Iconify sets that are "UI 24px + stroke + permissive" (a candidate shortlist) was not computed.

## 4. Delivery for Vue and accessibility

### Takeaway
Per-icon component imports are tree-shakeable and measured here at roughly 330 bytes per additional icon after a ~4 KB shared base; sprites and fonts add features (CSS-colour-only, shared cache) but fonts carry well-documented accessibility and fallback problems. Decorative icons should be `aria-hidden`; meaningful standalone icons need an accessible name on the interactive wrapper, not on the icon.

### Cited Findings
- **Own measurement (2026-10-27)**: esbuild (version not recorded), `--bundle --minify --format=esm --external:vue`, `@lucide/vue` 1.62.0. One icon (`House`): 4,028 bytes minified (1,900 gzip). Five icons (`House, Search, Settings, User, Trash2`): 5,366 bytes minified (2,326 gzip). Marginal ≈ 335 B minified per icon. `@lucide/vue` declares `"sideEffects": false`; installed size on disk is 32 MB, which is irrelevant to the bundle. — own-measurement
- Iconify JSON for Lucide: 1,978 entries (icons + aliases) in 600,791 bytes, an average of ~304 bytes per icon of raw JSON (before any compression). — own-measurement on `@iconify-json/lucide` (648 KB unpacked)
- Lucide's official docs state the library is ES-module based and tree-shakable: "Each icon can be imported as a Vue component, which renders an inline SVG Element. This way only the icons that are imported into your project are included in the final bundle." — [lucide docs via search](https://lucide.dev/docs/packages/lucide-vue-next) (snippet)
- Lucide also ships a font with stable code points (v1) and `lucide-static` with a sprite (`https://cdn.jsdelivr.net/npm/lucide-static@latest/sprite.svg` returns 200). — [v1.0.1 release notes](https://github.com/lucide-icons/lucide/releases/tag/1.0.1); own HTTP check
- Material Symbols as a font: 295 KB default, 7.9 MB without axis config, 1.7 KB when subset to named icons. — [Google Fonts docs](https://developers.google.com/fonts/docs/material_symbols) (primary)
- Runtime fetching: `@iconify/vue` defaults to the Iconify API; Nuxt UI notes uninstalled collections "load from the Iconify API at runtime". — see Section 3
- Icon fonts: screen readers may announce glyphs oddly ("black favorite star" best case, "unpronounceable" or skipped worst case); typeface-swapping tools for dyslexia replace icon glyphs; a failed font load shows a "missing character" glyph; SVG fails to a missing image rather than stray characters. — [Cloud Four, "Seriously, Don't Use Icon Fonts", 2015-11-23](https://cloudfour.com/thinks/seriously-dont-use-icon-fonts/) (secondary/opinion, 11 years old; the SVG-fragment support caveat in its comments is out of date)
- Accessibility defaults in Lucide: "Lucide icons are hidden from screen readers by default with `aria-hidden="true"`" (default since v1); decorative icons stay hidden; "If an icon carries meaning without nearby text or an interactive wrapper, give that icon an accessible label"; put the accessible name on the button using visually hidden text, which is "often more reliable" than `aria-label`; interactive targets at least 44×44 px; contrast at least 4.5:1; do not rely on colour alone. — [Lucide accessibility guide](https://lucide.dev/guide/advanced/accessibility) (primary)
- Sara Soueidan (2019-05-22): set `aria-hidden="true"` and `focusable="false"` on the icon; name the button via visually hidden text, `aria-labelledby` to a hidden span, or `aria-label` on the button; naming the SVG itself with `aria-label` or `<title>` "come with their failures in some browser / screen reader combinations". — [Accessible icon buttons](https://www.sarasoueidan.com/blog/accessible-icon-buttons/) (secondary, expert)

### Inferences
- For a component SDK on Vue 3: compiled per-icon components (what `@lucide/vue` and `unplugin-icons` emit) give tree-shaking with `sideEffects: false`, SSR-friendly inline SVG, and `currentColor` styling; no sprite or font is needed. Marginal per-icon cost (~0.3 KB minified) means a 200-icon app is order ~65 KB plus base, before gzip; this extrapolation is linear and not measured.
- SDK-level API suggestion drawn from the sources: an `Icon`/`<AppIcon>` wrapper that sets `aria-hidden="true"` and `focusable="false"` by default, and an `IconButton` that requires a visible or visually hidden label prop, so the "name goes on the button" rule is enforced in types.
- Sprite delivery would add cache sharing across the 35 apps but at the cost of an extra network request and cross-origin `<use>` limits (the latter is general knowledge, not verified here); not obviously worth it against ~0.3 KB/icon components.

### Gaps
- Tested only with esbuild and `@lucide/vue`; not measured with Vite/Rollup, `unplugin-icons`, or other sets; no third-party benchmark found.
- No evidence gathered on sprite vs component performance in Vue specifically.
- WCAG success criteria for non-text contrast (graphical objects) were not checked against the "4.5:1" figure Lucide's guide gives.

## 5. How design systems decide: own set vs adopted set, and governance

### Takeaway
The large design systems that were checked (Material, Carbon, Atlassian, Primer, Polaris) all keep their own icon set with a closed or gated contribution process. Smaller or framework-level systems adopt an existing set (Nuxt UI uses Lucide via Iconify). Lucide itself governs additions through written design rules and an issue/discussion template.

### Cited Findings
- Material: owns Material Symbols (Apache-2.0), a variable font with FILL/wght/GRAD/opsz axes; `google/material-design-icons` pushed 2026-10-23. — [Google Fonts docs](https://developers.google.com/fonts/docs/material_symbols), [GitHub API](https://api.github.com/repos/google/material-design-icons) (primary)
- Carbon (IBM): owns its icon set (2,638 icons in Iconify, Apache-2.0; `@carbon/icons-vue` 10.140.0). v10 contribution docs say icons must be unique ("not redundant with any existing icons in the system"), follow the IBM Design Language visual style, meet IBM accessibility standards, be usable across platforms and understood by a global audience; submissions as SVG "32px x 32px", whole-pixel, strokes expanded. A GitHub discussion on requesting new icons was answered by pointing to IBM Design Language site instructions. — [Carbon v10 icon contribution](https://v10.carbondesignsystem.com/guidelines/icons/contribute), [discussion #14940](https://github.com/carbon-design-system/carbon/discussions/14940) (snippet; current v11 docs not confirmed)
- Atlassian: built its own icon system. "Atlassian teams can contribute icons to our system for new designs and features"; the guide is limited to Atlassian employees. Questions before adding: Is it very similar to an existing system icon? Can an existing multi-purpose icon be used? Could it be confused with another concept? "Does the design need an icon at all, or would a text label, button, or other approach be clearer?" Icons are drawn "within a 16 × 16px bounding box" (16px default, 12px sparingly); colour via design tokens. `@atlaskit/icon` 38.0.2 (2026-09-29). — [Atlassian iconography](https://atlassian.design/foundations/iconography) (primary); [Atlassian blog on the new icon system](https://www.atlassian.com/blog/design/behind-the-screens-building-atlassians-new-icon-system) (snippet)
- Primer (GitHub): owns Octicons (780 icons, MIT; `@primer/octicons` 19.42.0, 2026-10-23); requests go through an icon-request issue template in `github/primer`; Primer's contribution page says "at this time, we are not looking for external contributions from non-GitHub staff". — [Primer contribute](https://primer.style/contribute), [Octicons README](https://github.com/primer/octicons) (snippet; forks quoted, upstream wording may differ)
- Polaris (Shopify): owns `@shopify/polaris-icons`, latest 9.3.1 on 2025-03-17 (19 months without a release); the contributing page `polaris.shopify.com/contributing/icons` returns a 301 redirect to `shopify.dev/docs/api/polaris`; an earlier version of the guide said new icons are added to both the Figma library and the icon package; the new admin design (Polaris 2.0 RC) "began rolling out progressively to merchants on September 15, 2026" and uses "new ... icons". — [npm registry](https://registry.npmjs.org/@shopify%2Fpolaris-icons) (primary); [redirect check on polaris.shopify.com](https://polaris.shopify.com/contributing/icons) (primary); [Polaris 2.0 changelog](https://shopify.dev/changelog/polaris-2-0-release-candidate) (snippet)
- Lucide's own governance: written design principles (24×24 canvas, 1px safe zone, 2px stroke, round joins, a rule "about consistent use of shapes"), a GitHub discussion template `icon-design.yml`, icon categories and tags in `categories/*.json`; maintainers reject whole categories (brand logos) for legal, design and maintenance reasons. — [design principles](https://raw.githubusercontent.com/lucide-icons/lucide/main/docs/contribute/icons/design-principles.md), [Lucide brand logo statement](https://lucide.dev/brand-logo-statement), [v1.0.0 release notes](https://github.com/lucide-icons/lucide/releases/tag/1.0.0) (primary)
- Adopters: Nuxt UI (Vue) defaults to Lucide through Iconify with optional offline bundling. — [Nuxt UI docs](https://ui.nuxt.com/docs/getting-started/integrations/icons/vue) (primary)

### Inferences
- Owning a set is what organisations do when icons carry brand identity and they have a design team; the common governance pattern in the sources is "check for duplicates → check the icon is needed → follow a single geometry spec → review → publish to Figma and package together".
- For this SDK, the nearest analogue to the big systems' process is a written spec modelled on Lucide's rules (24×24, 2px, round joins) and an "is there already an icon or is a label clearer?" gate before adding anything. Lucide's design-principles file is a ready template; ISC allows reuse of the code and files with notice (spec text reuse not checked).
- None of the five checked design systems adopts a third-party set wholesale; that is a size/brand-team effect and not evidence that adoption is wrong for a 35-app internal product family.

### Gaps
- Material's own governance for adding symbols (Google's process) was not retrieved.
- Carbon v11 icon contribution process: only v10 docs surfaced.
- Polaris icon governance after the 2026 redesign: unclear; icons package appears dormant on npm.
- The Atlassian "contribution" page showed contradictory text in two copies (new icons listed as both accepted and not accepted); first version judged more likely, not confirmed.
- No survey of Vue UI kits other than Nuxt UI (Vuetify, PrimeVue, Element Plus) was done.

## 6. Overall decision for the SDK: stay, aggregate, or scrape

### Takeaway
On the evidence collected, "scrape Font Awesome" is the weakest option: Free is already downloadable as CC BY 4.0 SVG with no scraping, and Pro cannot be put into a publicly distributed SDK under its quoted terms. The evidence favours staying on Lucide (upgrading to `@lucide/vue`) and adding a build-time, allowlisted supplement path through Iconify data (Tabler for filled/extra concepts, Simple Icons for brands) plus a custom collection for in-house icons.

### Cited Findings
- All findings above; see Sections 1–5. Key anchors: Lucide ISC and 103 releases in the last year ([Section 2](#2-coverage-and-consistency-counts-styles-grid-cadence-lucides-gaps)); Pro redistribution limits ([Section 1](#1-licensing-font-awesome-free-vs-pro-scraping-and-the-other-sets)); `unplugin-icons` builds only used icons ([Section 3](#3-aggregators-iconify-iconifyvue-unplugin-icons)); ~335 B marginal per icon (own measurement, [Section 4](#4-delivery-for-vue-and-accessibility)).

### Inferences
- Order of options by evidence: (1) stay on Lucide + allowlisted supplements (low legal risk, low cost, current upstream); (2) aggregate via Iconify data with a hard allowlist and a per-set licence file (more coverage, visual drift risk); (3) Font Awesome Free as an additional set (legal, but a second visual family with fill-heavy style); (4) Font Awesome Pro scraping (blocked by licence for a public SDK; **[lawyer]** if private-only); (5) own generation harness (outside this lane; the cost is design governance rather than licensing, and Lucide's published rules show what a spec costs).
- The question "would FA cover all use cases" cannot be answered without the inventory of icon names the 35 apps need; running that inventory against Lucide + Tabler + Simple Icons names would give the actual gap list.
- Lucide's v1 changes need a decision regardless of the option chosen: package rename, 14 removed brand icons, `aria-hidden` default (may change how existing apps label icon-only buttons).

### Gaps
- No owner-side data (current icon usage, how many distinct icons the 35 apps import, whether the SDK is publicly published on npm or private) was available to this lane; both change the licensing answer for Pro.
- No lawyer read on any of the above.
