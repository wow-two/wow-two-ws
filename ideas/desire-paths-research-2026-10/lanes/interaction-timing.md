## 2. Press vs release: OS menus, Radix / Reka UI / Headless UI / Ark UI, and pointerdown pitfalls

### Takeaway
The hypothesis is **half supported**. "Commit on a completed click so the user can abort" is backed by WCAG 2.5.2 (Level A) and by the menu libraries, which commit items on pointer-up. "Open cheap reversible things on pointerdown" is shipped mouse-only in Radix Select, Headless UI MenuButton and Reka Select (touch is excluded because pointerdown fires before a scroll is recognised), while Radix DropdownMenu and Reka Menubar open on pointerdown with no pointer-type check. It is not applied consistently within one library (Popover opens on click, Tabs on mousedown), and Zag/Ark and Reka's own DropdownMenu open on click.

### Cited Findings
**Standards and platform behaviour**
- WCAG 2.2 SC 2.5.2 Pointer Cancellation (Level A): for single-pointer functionality at least one must hold: No Down-Event (down-event executes no part of the function), Abort or Undo (completes on up-event, user can abort or undo), Up Reversal, or Essential. The Understanding doc calls up-event activation the most accessible way: the user can move away before releasing; the `click` event fires on release. Essential examples are keyboard emulation and timing-critical pianos/shooting games, and even then it recommends easy undo — [W3C WCAG 2.2 Understanding 2.5.2, primary](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html)
- MDN: `pointerdown` fires first and only later does the browser decide a gesture is a scroll/pan, after which `pointercancel` follows; reasons include panning/zooming/scrolling, `touch-action`, app switching, palm rejection. So `pointerdown` alone does not guarantee a press; completion belongs on `pointerup`, cancellation handling on `pointercancel` (the "avoid committing on pointerdown" advice came from my summariser, the event list is MDN's) — [MDN pointercancel, primary](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event)
- Win32 docs: pressing ENTER on a menu item "chooses the item as if the user released the mouse button while the item was selected", i.e. Windows menu items commit on button release; pointing at a submenu item opens the submenu without a click — [Microsoft Learn, About Menus, primary](https://learn.microsoft.com/en-us/windows/win32/menurc/about-menus)
- Classic Mac press-drag-release: press a menu title, drag, release over the item; Apple's legacy Menu Manager tracks the menu until the button is released; modern macOS accepts both click-click and press-drag-release (search excerpts, pages not read) — [Apple legacy Menu Manager, snippet](https://developer.apple.com/library/archive/documentation/mac/Toolbox/Toolbox-133.html); [Orion feedback 13725, snippet](https://orionfeedback.org/d/13725-some-popup-menus-do-not-support-click-drag-release-interaction); [1Password forum, snippet](https://discussions.agilebits.com/discussion/comment/398845)

**Speed gain**
- instant.page claims `mousedown` preloading gains about 80 ms on average over waiting for click, with zero unused requests; hover preloading after 65 ms leaves over 300 ms — [instant.page, opinion (vendor claim)](https://instant.page/). That ~80 ms is the only quantification found of the pointerdown-to-click gap.

### Inferences
- Verdict on the hypothesis: keep the second half as a rule (anything that commits, costs, or is hard to undo fires on completed click or on pointer-up over its own target). Treat the first half as an optimisation with a gate, not a rule: **mouse only (`pointerType === 'mouse'`, left button, no ctrl), touch/pen and keyboard on `click`/`keydown`** — the pattern Headless UI, Radix Select and Reka Select converge on.
- Industry practice does not follow "cheap and reversible means down": Popover (cheap, reversible) is click everywhere; Tabs is mousedown; Radix DropdownMenu is down (all pointer types) while Reka's DropdownMenu is click. The deciding factor in practice appears to be "emulates an OS menu" (press-drag-release), not cost or reversibility. The trade is about ~80 ms (vendor figure) per open against focus-management complexity: every pointerdown implementation needs `preventDefault`/focus workarounds (Radix dropdown L132, Headless use-handle-toggle L25-L32, Reka Select L131-L139).
- A strict reading of WCAG 2.5.2 treats any function started on down as needing an exemption. Opening a menu is abortable and undoable by closing, but I found no W3C text saying menu-open-on-down conforms; the mouse-only gate plus easy dismissal is the defensible position, not a documented pass.
- Press-drag-release is the part of OS menus worth copying alongside pointerdown-open: item commits on pointer-up over the item, with a hold (200 ms) and movement (5 px) guard so a plain click never counts as a drag-select (Headless numbers; Radix Select uses a 10 px threshold).
- Radix DropdownMenu's code has no pointer-type check, so on touch it should open at touch start, the behaviour issue 804 documented for Select. This is read from the code, not tested.
- Keyboard and assistive tech: Enter/Space on a native button produce `click`, not `pointerdown`, so a pointerdown-only handler would break them; all libraries add `keydown` openers (Radix L135-L141, Reka dropdown L62-L73). Screen-reader activation also commonly dispatches `click` only; not verified in a fetched source.

### Gaps
- Windows: no primary statement found on whether menu-bar menus open on mouse-down (the Win32 page only says items commit as on button release and submenus open on pointing). macOS evidence is search-snippet level.
- Not tested in a browser: touch-scroll behaviour of each trigger, Safari quirks, pointerdown vs click differences under assistive tech.
- Radix/Reka line numbers come from `main`/`v2` on 2026-10-27, not pinned release tags.

## 3. Our SDK (`@wow-two-beta/fe` 0.0.33): menus, popovers, selects

### Takeaway
The SDK does **not** use Reka UI or Radix: `package.json` has `@floating-ui/vue` only (no `reka-ui`, `radix-vue`, Headless UI or Ark), and the primitives are hand-made (`Primitive`, `Slot`, `DismissableLayer`) with Radix semantics ported from React (comments say "React's `onClick?.(e)` order"). **Every trigger opens on `click`**; `pointerdown` is used only for outside-dismiss, long-press, drag and gesture widgets. Menu items commit on click only, so press-drag-release is absent, and submenu intent is a fixed-delay timer with no grace polygon.

### Cited Findings
- Dependencies: only `@floating-ui/vue ^1.1.0` among overlay libraries; package `@wow-two-beta/fe` version `0.0.33` — `SDK/../package.json` lines 2-3 and 465

### Inferences
- Because the SDK is click-only, it carries none of the pointerdown pitfalls (touch-scroll opens, focus theft, keyboard gaps) and loses the ~80 ms gain and press-drag-release. A ported mouse-only `pointerdown` toggle (Headless UI `useHandleToggle` shape) would be a local edit in `DropdownMenuTrigger.vue`, `MenubarTrigger.vue` and (via `PopoverTrigger`) `SelectPicker`, leaving Popover/Modal/Tabs and all commit actions on click. This is a design option, not tested.
- Press-drag-release would need a quick-release composable on `Menu` (thresholds from Headless: 200 ms hold, 5 px move) because items listen to `click` only.
- Submenu navigation uses two fixed timers (100 ms open, 250 ms close) and no direction check, so a diagonal move toward a submenu across sibling rows can still switch rows after 250 ms; Radix/Reka ship a grace polygon for this (section 4).
- Prefetch-on-pointerdown (zero wasted requests, SvelteKit `tap` semantics) would complement the existing hover/focus warm-up, mostly for touch where hover does not exist.

### Gaps
- Not read: `Menu.vue` content-level key/selection flow outside the lines above, `ListboxPicker`/`Combobox` open triggers (they delegate to `PopoverTrigger` for `SelectPicker`; others not checked), and consuming apps' viewport meta tags (the 300 ms tap delay depends on them, section 4).

## 4. Delays and intent: double-click wait, tap delay, hover intent, prefetch, perceived performance

### Takeaway
Waiting is only justified when acting early would be harmful or ambiguous (Chen); the 300 ms tap delay is gone for mobile-optimised pages; hover intent has well-documented numeric defaults (65 ms prefetch, 100 ms/6 px hoverIntent, 300 ms menu-aim) and a geometric alternative to timers (grace polygon); prefetch gains ~80-300 ms depending on trigger; and the response-time thresholds (0.1 s / 1 s / 10 s, Doherty 400 ms) set the budgets that skeleton/spinner/optimistic choices serve.

### Cited Findings
**Double-click wait (Raymond Chen, 2009-04-29)**
- Some single-click actions wait about half a second to see whether a double-click follows; "Filtering out accidental double-clicks is informally known as debouncing". The wait exists because users who double-click everything would send the stray second click to a newly launched process or unowned top-level window (the new window appears without focus), whereas a modal dialog absorbs it harmlessly; single-clickers pay the wait. Rule implied: debounce only single-click actions whose result a second click would harm — [The Old New Thing, primary](https://devblogs.microsoft.com/oldnewthing/20090429-00/?p=18413)
- `GetDoubleClickTime` returns the user-configured maximum gap between two clicks, up to 5000 ms (the page does not state the default; Chen says "half-second") — [Microsoft Learn, primary](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getdoubleclicktime)

**300 ms tap delay**
- Mobile browsers waited about 300-350 ms between `touchend` and `click` to detect double-tap zoom; Chrome 32 (2014) removed it for mobile-optimised pages (`width=device-width`), Firefox and IE/Edge followed, and iOS 9.3 (March 2016) added a similar fix; `touch-action: manipulation` is the fallback (the post says Safari did not support it at the time). Author Jake Archibald; the page header shows "Last updated 2013-12-12" yet cites 2014-2016 events, so treat the date as unreliable — [Chrome for Developers, primary](https://developer.chrome.com/blog/300ms-tap-delay-gone-away)

**Hover intent and menu aim**
- hoverIntent (jQuery): waits until the cursor slows; defaults `interval` 100 ms (poll rate), `sensitivity` 6 px (max movement between polls to count as settled), `timeout` 0 ms (delay before the out-handler) — [hoverIntent docs, primary](https://briancherne.github.io/jquery-hoverIntent/)
- Kamens' `jQuery-menu-aim`: tracks the last 3 mouse positions; if the cursor is moving toward the open submenu (slope test against the submenu's upper and lower corners, `tolerance` 75 px) it delays activating a new row by `DELAY = 300` ms and re-checks, otherwise activates immediately; the README says delays and timeouts are the usual solution and direction detection makes row switching quicker — [jQuery-menu-aim source, primary](https://github.com/kamens/jQuery-menu-aim/blob/master/jquery.menu-aim.js) and [README, primary](https://github.com/kamens/jQuery-menu-aim/blob/master/README.md)
- Secondary summaries of Kamens' 2013 post: the "whack-a-mole" menu vanishes unless the cursor moves exactly horizontally; the common fix is a delay that makes menus feel sluggish; Amazon instead uses a triangle between the cursor and the submenu's corners; one commenter notes macOS uses intent and speed — [Webmaster Source, snippet](https://www.webmaster-source.com/?p=5035); [search excerpts, snippet](https://www.technologyreview.com/2013/03/09/179477/the-ingenious-engineering-trick-that-makes-amazon-menus-usable)
- Radix menu uses a pointer grace intent: it records the exit side and a polygon toward the submenu, and ignores pointer moves while the pointer moves toward the submenu inside that polygon — [radix menu.tsx L432, L484-L492, L1367-L1389](https://github.com/radix-ui/primitives/blob/main/packages/react/menu/src/menu.tsx#L484-L492)
- Reka `useGraceArea`: on `pointerleave` of trigger or content builds a convex hull from padded exit points and the target rect; in-transit state auto-resets after 300 ms; leaving the polygon or entering another grace trigger ends it — [reka useGraceArea.ts L6-L70](https://github.com/unovue/reka-ui/blob/v2/packages/core/src/shared/useGraceArea.ts#L6-L70)

**Prefetch on intent**
- instant.page: preload after 65 ms hover (over 300 ms average head start), or on `mousedown` (about 80 ms average, no unused requests), or `touchstart` on mobile (about 90 ms average); HTML only, honours data-saver, passive listeners, 1 kB — [instant.page, opinion (vendor claims)](https://instant.page/)
- SvelteKit `data-sveltekit-preload-data`: `hover` = on desktop when the mouse rests over a link, on mobile at `touchstart`; `tap` = at `touchstart` or `mousedown`; hover may fetch stale data when data changes quickly, so `tap` is suggested then; never preloads when `saveData` is set; no delay value documented — [SvelteKit link options, primary](https://svelte.dev/docs/kit/link-options)

**Perceived-performance thresholds**
- Nielsen: 0.1 s feels instantaneous (no feedback needed beyond the result); 1 s keeps flow of thought (show work in progress if slower); 10 s is the attention limit (needs percent-done, interrupt, estimate); based on Miller 1968 and Card et al. 1991; listed original date 1993-01-01 with a 2014 web update — [NN/g, primary](https://www.nngroup.com/articles/response-times-3-important-limits/)
- Doherty threshold: productivity peaks when responses come within about 400 ms (Doherty and Thadani, IBM Systems Journal, 1982, replacing a 2 s benchmark); takeaways include animation and progress bars to shorten perceived waits, and a deliberate delay can make a process feel more valuable (a persuasion tactic with an ethics caveat) — [Laws of UX, secondary](https://lawsofux.com/doherty-threshold/)
- Skeletons vs spinners (NN/g, Samhita Tankala, published 2023-06-04, last reviewed 2026-09-02): skeletons for full-page loads under about 10 s; not needed under 1 s (a flash feels like users cannot keep up); spinners for single modules, roughly 2-10 s; progress bars for longer or process-type waits and above 10 s; the evidence cited is one 2018 study without methods, and skeletons "do not replace performance-optimization efforts" — [NN/g, primary](https://www.nngroup.com/articles/skeleton-screens/)
- A 2017 Viget study, reported secondhand, found skeletons performed worst on perceived wait and task time and concluded they are "not a silver bullet" — [search excerpt, snippet](https://www.nngroup.com/videos/skeleton-screens-vs-progress-bars-vs-spinners/)
- Optimistic UI: React `useOptimistic` shows a temporary value while an Action is pending; on success the real value takes over in the same render; on failure the UI reverts to the previous value; failure reverts silently so the author must show an error; use reducers/relative updates to avoid stale values — [React docs, primary](https://react.dev/reference/react/useOptimistic)

### Inferences
- Chen's rule generalises: delay a single action only if the extra input could cause harm; otherwise make the first action cheap and idempotent so the second input upgrades it (select on click, open on double-click) with no wait.
- For menus a geometric test beats fixed timers: both Radix and Reka implement a grace polygon, and Kamens' own implementation still uses a 300 ms fallback delay only while the cursor heads toward the open submenu. The SDK's 100/250 ms timers (section 3) are the "timeouts and delays" approach the README calls the usual one.
- Hover prefetch should wait for intent (about 65 ms in instant.page, hoverIntent-like settling) for expensive fetches, while chunk prefetch (small, deduplicated) can fire on enter. Pointerdown/`touchstart` prefetch is the zero-waste option and the main one for touch.
- Budgets for SDK loading states: under 100 ms show nothing extra; around 1 s show a spinner (module) or skeleton (page); beyond about 10 s, progress with an estimate. The Doherty 400 ms figure matches a "no skeleton flash before about 400 ms" delay but that exact delay is not stated by the sources.
- Optimistic UI is the one technique on this list that is literally "lying": it shows a result before the server confirms, so it needs the failure path (revert plus message) and should be limited to actions that rarely fail and are reversible.

### Gaps
- Kamens' post text itself (bot challenge), the delay/threshold figures in it beyond the plugin code, and the video's treatment of them.
- Default values of platform constants: Windows drag threshold (`SM_CXDRAG`), Windows default double-click time, Android tap/long-press/double-tap timeouts — not fetched.
- Next.js `Link` prefetch behaviour not fetched; the Nuxt `NuxtLink` docs URL returned 404.
- No source quantifying how many ms a typical mouse click holds between down and up, other than instant.page's vendor claim.

## 5. Competing actions on one element: single vs double click, click vs drag, tap vs long-press

### Takeaway
Good products avoid adding delay by letting the first action be cheap and compatible with the second (Chen's launch case is the exception that needs a wait), by deciding click vs drag with a small movement threshold rather than time, and by treating long-press as an additive gesture that arms a timer only when someone listens. Cancellation events (`pointercancel`, `pointerleave`) are part of the disambiguation, not an edge case.

### Cited Findings
- Single vs double click: the delayed-action case exists only for single-click actions that launch a process or unowned window; modal-dialog single-click actions need no wait — [The Old New Thing, primary](https://devblogs.microsoft.com/oldnewthing/20090429-00/?p=18413)
- Tap vs double-tap: the browser tap delay was a double-tap-zoom wait; opting into a mobile viewport or `touch-action: manipulation` removes the wait by giving up double-tap zoom (pinch-zoom stays) — [Chrome for Developers, primary](https://developer.chrome.com/blog/300ms-tap-delay-gone-away)
- Click vs drag (menu context): Headless UI treats a pointer sequence as press-drag-release only after at least 5 px of movement and more than 200 ms of hold; below either it is a normal click — [headlessui use-quick-release.ts L22-L33](https://github.com/tailwindlabs/headlessui/blob/main/packages/@headlessui-react/src/hooks/use-quick-release.ts#L22-L33). Radix/Reka Select use a 10 px threshold from the opening pointerdown to decide whether a `pointerup` selects — [radix select.tsx L760-L775](https://github.com/radix-ui/primitives/blob/main/packages/react/select/src/select.tsx#L760-L775); [reka SelectContentImpl.vue L139-L188](https://github.com/unovue/reka-ui/blob/v2/packages/core/src/Select/SelectContentImpl.vue#L139-L188)
- Tap vs long-press: Zag's context-menu trigger starts on touch `pointerdown` and cancels on `pointermove`, `pointerup`, `pointercancel` (mouse is excluded) — [zag menu.connect.ts L174-L193](https://github.com/chakra-ui/zag/blob/main/packages/machines/menu/src/menu.connect.ts#L174-L193); Reka's trigger starts a timer with `pressOpenDelay` — [reka ContextMenuTrigger.vue L104-L111](https://github.com/unovue/reka-ui/blob/v2/packages/core/src/ContextMenu/ContextMenuTrigger.vue#L104-L111)
- SDK precedents: 500 ms default long-press with a 200 ms floor "overlaps with normal click latency" (`SDK/foundation/dom/PressExtensions.ts:10-18`); the long-press timer is armed only when a `long-press` listener exists and a fired long-press suppresses the following click (`SDK/presentation/actions/button/Button.vue:363-380, :433, :446`); context menu 600 ms and 8 px (`ContextMenuTrigger.vue:17, :118`); `useLongPress` uses a 10 px tolerance because "no real touch is still" and listens on `window` so leaving the element cancels the hold (`UseLongPress.ts` header)
- `pointercancel` fires when the browser takes the pointer for scrolling/panning, `touch-action`, interruptions or palm rejection; handle it as "interaction over without release" and discard in-progress state — [MDN, primary](https://developer.mozilla.org/en-US/docs/Web/API/Element/pointercancel_event)
- Radix Select calls `releasePointerCapture` on the trigger so implicit capture does not interfere with the content's pointer tracking — [radix select.tsx L403-L411](https://github.com/radix-ui/primitives/blob/main/packages/react/select/src/select.tsx#L403-L411)
- WCAG 2.5.2: an abortable up-event commit is a conformant way to resolve a press whose target the user may want to leave — [W3C, primary](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html)

### Inferences
- Disambiguation without delay, ordered by preference: (1) make the first action a safe subset of the second (select, then open); (2) disambiguate click vs drag by distance (about 5-10 px) rather than time; (3) gate pointerdown shortcuts by pointer type so touch scroll never competes; (4) use a hold only for an additive gesture and arm it only when a handler exists; (5) wait for a second input only when an early action would be harmful (Chen). Fixed waits remain for press-count gestures such as the AirPods example in the video description, which I could not confirm.
- Any pointerdown-driven feature needs a paired cancel path (`pointercancel`, leave, Escape) — the SDK's gesture composables already document this for `touch-action`.

### Gaps
- The LIE video's treatment of AirPods press-count timing and drag-and-drop was not verified (no transcript).
- No fetched source for platform drag-start thresholds or single/double-press windows on mobile OSes.
