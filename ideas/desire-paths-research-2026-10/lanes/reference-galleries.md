# Reference galleries and design-system doc sites: how they organize, present and surface components

Research date: 2026-10-27. Method: WebFetch (small-model page summaries), the Claude browser pane (rendered page text + DOM probes, one screenshot each for Primer and Apple HIG), and WebSearch. Where a site blocked or failed, it is listed under that question's Gaps. Layout facts such as aspect ratios, colours and exact grid columns are reported only where a source stated them; otherwise they are marked unverified.

## 1. How do the reference galleries (Mobbin, Page Flows, Refero, SaaSFrame, Nicely Done, UI Sources, Land-book, Lapa Ninja, Component Gallery) organize content, filter, search, show cards, save, and handle light/dark and platform?

### Takeaway
The app-screenshot galleries (Mobbin, Page Flows, Refero, SaaSFrame, Nicely Done) all converge on the same 4-5 content axes: whole screens, flows, UI elements/patterns, apps/sites, with page-type and industry as secondary facets; the landing-page galleries (Land-book, Lapa Ninja) organize by site category and section. Component Gallery is the odd one out and the closest to our goal: a text-first index of ~60 canonical component names with alias lists and a per-component list of real examples pulled from ~95 design systems, with facet chips that carry counts.

### Inferences
- Borrow from Component Gallery: one canonical name plus an "Also known as" alias list on every card/page, and a name-distribution chart; they solve the "what do we call it" problem without forcing a single name. Aliases should also feed search (cf. Mobbin's synonym search).
- Borrow from Mobbin/SaaSFrame/Nicely Done: counts next to every facet value, a caption of the form `{Component} - {Layout/where}` (Nicely Done's "Screen type - App name"), saved collections, and "similar" or "saved in" cross-links. Persist active filters when the user switches content type or platform (Mobbin 2023-06).
- Four orthogonal axes recur (page/screen type, flow/task, pattern, UI element); our card already has two of them (component = UI element, layout = screen type). A "task/flow" axis (e.g. "Ask users for...") would match GOV.UK's patterns and the galleries' flows.
- Pitfall: Mobbin needed an explicit fix because adding a second facet after choosing a category dead-ended; design facets as additive from the start.
- Pitfall: a gallery with ads/sponsored cards (Land-book, Lapa Ninja) or paywalled facets (Page Flows, SaaSFrame) is not a concern for an in-house tool, but the "gated search" complaint in section 5 is a warning that search must work fully for every viewer.
- Light/dark and platform: none of the sources shows per-screenshot light/dark variants as a first-class facet except Refero's "Dark Mode" tag; platform is a top-level switch (Page Flows, Refero, Mobbin) that persists filters. For a Vue component gallery, a global theme toggle that re-renders the live layout (rather than swapping screenshots) is the stronger option; this is an inference, not a sourced practice.

### Gaps
- Mobbin's own explore/UI-elements/glossary pages return 403 to both WebFetch and the browser pane (bot wall), so Mobbin's card anatomy (image ratio, metadata) and its UI-element term list could not be read. Only the changelog and home page were readable.
- Land-book's meaning of the small integer on each card is unlabeled in extracted text (could be likes/saves); Lapa Ninja's filter UI was not captured (only the home feed).
- Aspect ratios and colours are unverified for everything except Nicely Done's 576x310 image attribute.
- Page Flows/SaaSFrame/Refero filter UIs behind login or paywall were not seen; facet behaviour is inferred from marketing pages.
- Whether Refero's "Styles" and Mobbin's "Sites" present sections as cropped components could not be confirmed.

## 2. How do Material 3, Apple HIG, Atlassian, Polaris, Primer, Carbon, GOV.UK, Spectrum, Fluent 2, Nuxt UI and shadcn/ui structure a component page, and which use anatomy or "in context" imagery with the component highlighted and the surroundings muted?

### Takeaway
Every major system has an overview/usage section, anatomy (numbered or labelled), do/don't, accessibility and related components, but they split them differently: tabbed (M3, Carbon, Atlassian, Primer, Fluent) vs one scrolling page (HIG, GOV.UK, Ant, Nuxt UI, shadcn). I found no mainstream system that uses the specific technique "featured component in colour, rest of the screen grayed out"; the nearest techniques are numbered anatomy callouts, emphasised-part anatomy diagrams (Primer), correct/incorrect image pairs (HIG, M3), and the real UI's own scrim dimming (HIG sheets, M3 dialog). That technique is therefore a differentiator for our gallery.

### Cited Findings

#### Page structures observed (component = dialog/modal where possible for comparability)
- Material 3 Dialogs: four tabs Overview / Specs / Guidelines / Accessibility. Overview = one-line definition ("Dialogs provide important prompts in a user flow"), bullet summary, an "Availability & resources" table (Figma design kit, Flutter, Jetpack Compose, Android Views, Web, each with a status), "Differences from M2" (colour, layout, position, shape, typography). Guidelines = Usage, Anatomy (numbered parts per variant: Container, Icon, Headline, Supporting text, Divider, Buttons, Scrim), Basic dialog, Full-screen dialog, Adaptive design, Behavior; guidance is interleaved with captioned Do / Don't / Caution items (check, close and exclamation icons) and a "Similar components" comparison table. — [M3 overview](https://m3.material.io/components/dialogs/overview); [M3 guidelines](https://m3.material.io/components/dialogs/guidelines)
- Apple HIG Alerts: single page; one-sentence definition, then Best practices (each a bold lead sentence plus rationale and a real-app example, e.g. Mail's connection indicator), Anatomy (platform switcher iOS / macOS / tvOS / visionOS / watchOS), Content, Buttons, then Platform considerations, Resources, Change log; a right rail lists supported platforms with icons and an on-page nav. Left nav is a filterable tree. — [HIG Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts); [HIG Sidebars (nav and rail observed in browser pane)](https://developer.apple.com/design/human-interface-guidelines/sidebars)
- Apple HIG imagery: correct/incorrect pairs are tagged with small badge images (alt text "An X in a circle to indicate incorrect usage" / "A checkmark in a circle to indicate correct usage"); images ship in light/dark variants (`~dark@2x` file names); sheet imagery shows a real app (Notes) with the sheet over "a dimmed Notes document". — [HIG Sidebars JSON-backed page](https://developer.apple.com/design/human-interface-guidelines/sidebars); [HIG sheets data](https://developer.apple.com/design/human-interface-guidelines/sheets)
- Atlassian Modal dialog: four tabs Examples / Code / Usage / Changelog. Usage = Usage, Parts (anatomy diagram with numbered list: header with h1 title, close button, body, footer), Accessibility (severity, labelling, dismissing, focus order), Best practices (button alignment, simple and focused, nesting) as Do/Don't pairs, Content guidelines, Related (Popup, Custom modal or Spotlight, Inline message, each with a one-line "use it for" reason). Examples tab = live "Open modal" demos with collapsible code and "Edit in code sandbox", no do/don't. — [Atlassian usage](https://atlassian.design/components/modal-dialog/usage); [Atlassian examples](https://atlassian.design/components/modal-dialog/examples)
- Carbon Modal: tabs Guidelines / Specifications / Code / Accessibility. Guidelines order: Live demo (theme and variant selectors), Overview (When to use, Variants, Feature flags), Formatting (Anatomy, Sizing, Alignment), Content, Universal behaviors, Modal variants, AI presence, Related ("Modal versus notification", Components, Patterns), Feedback. Anatomy = captioned diagram image ("Modal anatomy diagram") followed by a numbered list of five parts; no Do/Don't labels, guidance is prose, bullets and captioned example images (18 images on the page, e.g. "Modal sizes", "Modal focus example", light and dark AI-presence examples). — [Carbon modal](https://carbondesignsystem.com/components/modal/usage/) (redirects to `/building-blocks/core/components/modal/guidelines`)
- GitHub Primer ActionMenu: tabs Overview / Guidelines / Accessibility. Overview = platform readiness badges (React "ready", Rails "ready"), per-platform links (Storybook, Source, Usage; Docs, Lookbook, Source), "View in Figma", React examples (8 named plus "More code examples", each a live demo with Copy, Reset and "Open in StackBlitz" plus code editor), Props, Related components (ActionList, Button, IconButton, SelectPanel). Guidelines = Anatomy then Content subsections (avoid input controls, icons, trailing visuals, multi-level, inactive items). — [Primer overview](https://primer.style/product/components/action-menu/); [Primer guidelines](https://primer.style/product/components/action-menu/guidelines/)
- GOV.UK Radios: one page: When to use, When not to use, How it works (many sub-sections, each with an example), Research on this component, Recent changes (version table), Help improve this component, Need help. Every example has "Open this example in a new tab" and HTML / Nunjucks code tabs. No anatomy section and no Related section; related components are inline links. — [GOV.UK Radios](https://design-system.service.gov.uk/components/radios/)
- Fluent 2 React Dialog (Usage): intro with alternatives, resource links (Storybook, WAI guidance), live demo with theme selector, Types (Modal, Non-modal, Alert, each with "use it when"), Behavior (dismissal, scrolling, forms), Layout (header, body, footer), Accessibility (nesting, focus), Content. — [Fluent 2 Dialog](https://fluent2.microsoft.design/components/web/react/core/dialog/usage)
- Shopify Polaris (now web components on shopify.dev) Button: intro, "Use cases" (four bullets), Properties (events, slots), Examples (11 H3s), Best practices, Limitations; related components appear only inline. The old `polaris-react.shopify.com` URLs now 301 to `shopify.dev/docs/api/polaris`. — [Polaris Button](https://shopify.dev/docs/api/app-home/polaris-web-components/actions/button); [Polaris redirect](https://polaris-react.shopify.com/components)
- Ant Design Modal: a short "When To Use" paragraph first, then Examples and API. — [Ant Design Modal](https://ant.design/components/modal)
- Nuxt UI Modal: Usage, Examples, API (Props, Slots, Emits), Theme, Changelog; Note/Tip/Warning/Caution callouts; no when-to-use or related section. — [Nuxt UI Modal](https://ui.nuxt.com/docs/components/modal)
- shadcn/ui Dialog: Installation (CLI/manual tabs), Usage, Composition, named examples, RTL, API Reference; each example = live preview plus Copy and "View Code"; no related or when-to-use. — [shadcn Dialog](https://ui.shadcn.com/docs/components/dialog)

#### The anatomy / in-context imagery question
- Numbered anatomy callouts with a key are the dominant technique: M3 lists numbered parts per variant; Carbon pairs a diagram with a numbered list; Atlassian pairs a diagram with a numbered list; Atlassian's own Confluence design-component template instructs authors to upload an anatomy diagram with numbered callouts and define each element. — [M3](https://m3.material.io/components/dialogs/guidelines); [Carbon](https://carbondesignsystem.com/components/modal/usage/); [Atlassian](https://atlassian.design/components/modal-dialog/usage); [Atlassian template via search](https://wac-cdn.atlassian.com/software/confluence/templates/design-component)
- Primer's anatomy is the closest to "highlight" styling: the figure's alt text says "Several elements are emphasized, such as the trigger, actions, overlay menu, trailing visual shortcuts, trailing visual submenu indicator, and the 3 dot dialog indicator"; in the browser the diagram is a rendered open menu on a pale grey panel with purple pill labels ("trigger", "ActionList", "Overlay menu") joined by connector lines. The component is shown alone, not inside a muted page. — [Primer guidelines](https://primer.style/product/components/action-menu/guidelines/) (observed in browser pane 2026-10-27)
- M3 describes the dimming as component behaviour, not as doc technique: "surfaces behind the container are scrimmed with a temporary overlay to make them less prominent", illustrated as "Basic dialogs appear over a background scrim". — [M3 guidelines](https://m3.material.io/components/dialogs/guidelines)
- A StackBlitz guide lists static screenshots, interactive demos and before/after comparisons as the visual-example formats and says realistic content helps screenshots; it does not mention highlight-and-mute. — [StackBlitz blog](https://blog.stackblitz.com/posts/design-system-component-documentation/)

### Inferences
- Page skeleton to borrow (the intersection of the best ones): one-line definition and when-to-use up top (M3, Ant, GOV.UK); a live demo; anatomy; Do/Don't; a "Similar components / use X instead" table (M3, Atlassian Related, Fluent intro); accessibility; related; and a changelog/status strip (M3 "Availability & resources", Primer readiness badges, GOV.UK Recent changes).
- Tabs vs scroll: the systems with the richest pages (M3, Carbon, Atlassian, Primer) separate Overview / Guidelines / Code / Accessibility into tabs so that designers and developers each land on their section; scroll-only pages (Nuxt UI, shadcn) are developer-only and have no rationale. Our philosophy page serves a mixed audience, so a short top summary plus anchor TOC is safer than hiding rationale behind a tab.
- Highlight-and-mute is novel relative to these sources (I found none using it). Closest visual precedents to cite when pitching it: Primer's emphasised-part anatomy, HIG's real-app sheet over a dimmed document, M3's scrim. Our card can legitimately claim it as new; the risk is that nothing proves users find it clearer, so test it against a plain anatomy callout.
- Apple's light/dark image variants (file-name convention) suggest generating both theme renders of each layout rather than one.

### Gaps
- Adobe Spectrum: `spectrum.adobe.com/page/dialog/` and `/page/alert-dialog/` return 404 in the browser pane and a search for the current structure returned unrelated results; Spectrum's page structure is not documented here.
- Polaris's old (pre-2025) component pages with Best practices / Content guidelines / illustrated do-don't could not be read (`web.archive.org` is blocked for the fetcher; polaris-react redirects). Only the new web-components page is described.
- Primer's "when to use / when not to use" content, if present, was not seen; only the Overview and Guidelines headings were read.
- M3 images did not render in my browser pane (blank screenshot), so M3's anatomy figure style (isolated component vs in context, colours) is unverified. HIG, Carbon and Atlassian image content is known only from alt text/captions, not visually.
- Page text came via summarizing fetchers; do/don't visual layout (side-by-side vs stacked, border colours) was not verified for any site.

## 3. How do these sites present the full component list (illustrated cards vs text list), what does each card carry, and how do category taxonomies compare?

### Takeaway
Index pages split three ways: illustrated card grids (Carbon, Component Gallery since 2022, Ant Design, Atlassian cards with descriptions), name plus one-line description lists (M3, Fluent 2, Nuxt UI, Vuetify), and bare alphabetical text links (GOV.UK, shadcn/ui). Category names are not standardised; the common core is Navigation, Forms/Inputs, Feedback/Messaging, Layout, Data display, and Overlays, but several systems (Carbon, Primer, GOV.UK, shadcn) skip categories and rely on an alphabetical list plus search.

### Inferences
- Only three category names recur across the five fully read taxonomies: Navigation (M3, Atlassian, Ant, Nuxt, Vuetify, Page Flows), Layout (Atlassian, Ant, Nuxt, HIG "Layout and organization"), and a feedback group (Ant "Feedback", Atlassian "Messaging", Page Flows "Display & Feedback"). Overlays is separate in Atlassian and Nuxt, absorbed under Feedback in Ant and Containment in Vuetify. A gallery that must show a component's category should pick one scheme and expose the alias in search, since "Modal" lives under Feedback, Overlay, Containment and Presentation depending on the site.
- A catch-all bucket ("All other components", "Other", "Primitives") appears in M3, Ant and Atlassian; it signals taxonomy debt and should be avoided or kept near-empty.

The few that add an illustration (Carbon, Ant, Component Gallery) add no further metadata, so a status label (Atlassian) and a "version added" tag (Ant) are the rare, useful extras; our cards can add category and "where used" on top.

## 4. Which sites document principles/rationale per component ("where to use", "philosophy"), and how do they show where a component appears in real product screens?

### Takeaway
"When to use / when not to use" is near universal (GOV.UK, M3, Ant, Carbon, Polaris "Use cases", Atlassian Related), but explicit rationale ("why this exists", "research on this component") is rare: GOV.UK is the standout, HIG explains reasons inline in best-practice prose, and the Component Gallery feature filter shows only 2 of 95 design systems tagged "Research". Real-product placement is shown mostly by the galleries (Mobbin, Refero, SaaSFrame), by HIG's real-app screenshots, and by GOV.UK/Carbon pattern pages, not by component pages.

### Cited Findings
- GOV.UK: each component page has When to use, When not to use, How it works, and a "Research on this component" section that invites readers to share findings via a GitHub discussion; plus "Recent changes" and "Help improve this component". Patterns are separate pages for "best practice design solutions" to specific tasks and page types, which "often use one or more components". — [GOV.UK Radios](https://design-system.service.gov.uk/components/radios/); [GOV.UK patterns](https://design-system.service.gov.uk/patterns/)
- Material 3: Usage states a stance ("Dialogs are purposefully interruptive, so they should be used sparingly"), gives a Do/Don't ("Don't use dialogs for low- or medium-priority information. Instead use a snackbar"), and a "Similar components" table that compares Snackbar vs Dialog on Importance and Action needed, described as a "component messaging strategy" to avoid overusing dialogs. "Differences from M2" lists what changed and why (corner radius, padding). — [M3 guidelines](https://m3.material.io/components/dialogs/guidelines); [M3 overview](https://m3.material.io/components/dialogs/overview)
- Apple HIG: every best practice is a bold directive followed by rationale and a concrete product example: alerts should be used sparingly because they interrupt; do not alert for common undoable actions; avoid alerts at app start; "Avoid using an alert merely to provide information" with Mail's indicator as the alternative. — [HIG Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)
- Fluent 2: intro positions the component against neighbours ("If you need to give someone an update ... try a toast ... additional context ... try a popover"); each type has a "use it when" with a real scenario (signing into an app; find and replace). — [Fluent 2 Dialog](https://fluent2.microsoft.design/components/web/react/core/dialog/usage)
- Atlassian: Related section routes to Popup, Custom modal or Spotlight (onboarding), Inline message, each with a one-line reason; Best practices as Do/Don't pairs. — [Atlassian usage](https://atlassian.design/components/modal-dialog/usage)
- Carbon: Overview has "When to use"; Related has "Modal versus notification"; the page includes variant-by-intent sections (passive, transactional, danger, acknowledgment, progress). — [Carbon modal](https://carbondesignsystem.com/components/modal/usage/)
- Ant Design: "When To Use" is the first block on the page, a two-sentence rationale ("without jumping to a new page and interrupting the user's workflow"). — [Ant Design Modal](https://ant.design/components/modal)
- Polaris: "Use cases" (four bullets), "Best practices", "Limitations". — [Polaris Button](https://shopify.dev/docs/api/app-home/polaris-web-components/actions/button)
- Component Gallery: "Usage guidelines" per component plus a Features tag per design system (Code examples 79, Open source 69 ... Research 2); the component page links out to each design system's own page for real usage rather than showing screens. — [component.gallery/accordion](https://component.gallery/components/accordion/); [design systems list](https://component.gallery/design-systems/)
- Real-screen context in galleries: Nicely Done captions each preview "Screen type - App name"; SaaSFrame has a Patterns taxonomy (Modal 519 screens, Text Input 910) tied to real SaaS apps; Refero and Mobbin list UI Elements beside Screens/Flows; Mobbin's "Saved in" shows which collections contain a screen. — [nicelydone.club](https://nicelydone.club/); [saasframe.io](https://www.saasframe.io/); [refero.design](https://refero.design/); [Mobbin changelog](https://mobbin.com/changelog.md)
- Real-screen context in design systems: HIG uses real apps (Notes sheet over a dimmed document, Music in visionOS with a sidebar and playlists grid); GOV.UK Patterns are full page types (confirmation pages, question pages); M3 pairs Do/Don't items with images (the page's Do/Don't blocks are captioned examples; image content not verified). — [HIG Sheets data](https://developer.apple.com/design/human-interface-guidelines/sheets); [HIG Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars); [GOV.UK patterns](https://design-system.service.gov.uk/patterns/); [M3 guidelines](https://m3.material.io/components/dialogs/guidelines)

### Inferences
- A "philosophy" page maps cleanly onto four proven blocks: Why it exists (GOV.UK Research, M3 Differences from M2), When to use / not to use (GOV.UK, Ant, M3 Usage), Instead use X (M3 Similar components table, Fluent intro, Atlassian Related), and Where it appears (HIG real apps, GOV.UK pattern pages, Component Gallery examples list). The "desire path" angle (what user behaviour the component formalises) has no direct precedent in the pages I read; the nearest are GOV.UK "Research on this component" and HIG's "people do X, so..." rationales. I searched for the term in design-system docs only indirectly (via the pages above) and did not find it used; treat "desire path" as an original framing.
- Best rationale style to imitate: HIG's bold-directive-then-reason bullets and M3's importance table. Both stay short and tie the rule to a real behaviour or neighbour component.
- Real context is mostly a gallery capability, not a design-system one; our card (component highlighted inside a realistic layout) merges the two, which none of the sources do.

### Gaps
- No page found that explicitly documents a user behaviour or "desire path" per component; absence is based on the pages above, not an exhaustive crawl.
- Carbon, Atlassian and Primer pattern pages (task flows with real examples) were not read.
- How Polaris's older "Best practices" section shows illustrated do/don'ts could not be read (see Q2 gaps).

## 5. What do practitioners praise or complain about (findability, too much prose, stale screenshots, missing real-world context)?

### Takeaway
Practitioner commentary is thin on primary data and heavy on vendor blogs, but it is consistent: component docs fail when they are bloated or abstract, concrete examples fix much of that, images go stale and cost maintenance, and unlisted or newer components are misused. For the galleries, complaints concentrate on paywalls, shallow free tiers, per-category depth, and ad/sponsor clutter; Mobbin's own changelog shows facet dead-ends and search quality as areas that needed repeated rework.

### Cited Findings
- zeroheight's Design Systems Report 2026 presents documentation as both the biggest pain point and the clearest opportunity; the page does not expose percentages. — [zeroheight report 2026](https://webinars.zeroheight.com/watch/zeroheight-design-systems-report-2026-the-findings) (as summarised in search results)
- zeroheight's help centre says too much documentation means people are less likely to read it, too little means they find no value, and advises asking intended readers. — [zeroheight help](https://help.zeroheight.com/hc/en-us/articles/54409088315163) (as summarised in search results)
- Ramotion lists "too much theory, too few concrete examples" as a failure mode that leads designers and developers to ignore docs. — [Ramotion guide chapter 7](https://www.ramotion.com/blog/design-system-guide-chapter-7-documentation-and-tools/) (as summarised in search results)
- EightShapes (summarised in search results; direct fetch failed) recommends Do/Don't image pairs as a break from text, warns too many images overwhelm the page, suggests roughly one picture per five to ten text-only guidelines, and notes images get out of date and cause maintenance headaches. — [EightShapes component design guidelines](https://eightshapes.com/articles/component-design-guidelines/)
- UX Collective tips: ask "Would an example work better here?" and turn dense paragraphs into lists. — [UX Collective](https://uxdesign.cc/6-tips-for-writing-effective-design-system-documentation-11c35b44169) (as summarised in search results)
- StackBlitz's component-doc guide names these pitfalls: components hidden from navigation are harder to find; newer or unfamiliar components shipped without usage guidance get misused; read-only examples cannot show every combination; docs for the latest version read by users on older versions; no clear contact channel. It does not mention stale screenshots. — [StackBlitz blog](https://blog.stackblitz.com/posts/design-system-component-documentation/)
- Mobbin complaints: a June 2026 Trustpilot reviewer says the free account gives nearly nothing and the paywall is constantly in your face; others say only 10-20 apps per category, "slow" and "basically just screenshots", web and iOS only; billing and cancellation confusion (no pro-rata refund on annual plans). Praise: the keyword search is valued and the interface is clean and fast (an affiliate-linked review, not independent). — [Trustpilot (ES)](https://es.trustpilot.com/review/mobbin.com); [Coolcuration review (affiliate)](https://coolcuration.com/mobbin-review-is-it-worth-it)
- A conversion-rate case study found free Mobbin users often scrolled far down the pricing page to judge the volume of assets, i.e. volume itself is the value signal people look for. — [CRE Mobbin win report](https://conversion-rate-experts.com/mobbin-sticky-header-win-report/)
- Search quality as an ongoing project at Mobbin: synonym search (2023), "dead-end" fix (2025), visual search (2025), plain-language and Deep Search (2026), i.e. keyword search alone was not sufficient. — [Mobbin changelog](https://mobbin.com/changelog.md)
- Staleness signalling in galleries: Component Gallery added an "Unmaintained" badge for systems with no meaningful updates in a year and sorts design systems by most recently reviewed. — [Component Gallery changelog](https://component.gallery/changelog/)
- Competitor-authored comparisons say Land-book covers only landing and marketing pages (no app screens or flows) and that Lapa Ninja's catalogue is larger; treat as biased. — [Lazyweb vs Land-book](https://www.lazyweb.com/vs/land-book.md)
- Gallery clutter: Land-book shows ads in the feed (removable with PRO) and Lapa Ninja interleaves "Sponsored" and "Ad" cards with editorial ones. — [land-book.com](https://land-book.com/); [lapa.ninja](https://www.lapa.ninja/)

### Inferences
- Pitfalls to design against: (1) prose-heavy pages with no concrete example up top; (2) stale screenshots, which only a rendered-from-source preview avoids (our gallery's layouts should be live Vue renders, not images); (3) components missing from navigation or index; (4) facets that dead-end; (5) search limited to exact names (aliases and synonyms needed); (6) an open-ended "Other" bucket; (7) docs that do not say which version they describe.
- Praised patterns to copy: examples before explanation, a one-image-per-handful-of-guidelines ratio (EightShapes), visible freshness/status signals (Component Gallery "Unmaintained", Atlassian status labels, M3 availability table), and large visible counts as a trust signal (Mobbin finding).
- None of the sources compares doc sites by usability study data; the evidence is anecdotal (blogs, reviews). No quantified findability metrics were found.

### Gaps
- zeroheight report percentages and any findability-specific statistics are not available (results page only).
- No Smashing Magazine or NN/g article specifically comparing component doc sites was found in the searches run.
- EightShapes direct fetch failed (DNS), so its claims are second-hand via search summaries; verify before quoting.
- Mobbin staleness (outdated screens) complaints: no source found either way.
- Trustpilot reviews are self-selected; the Mobbin review on Coolcuration is affiliate-linked.
