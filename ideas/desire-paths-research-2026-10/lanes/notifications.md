# Notifications vector for a Vue 3 component SDK: toasts, undo, rich content, actions, pinned progress, timing and stacking

Researched 2026-10-27. Source tags used inline, as in the other lanes: **[primary]** = vendor/spec docs, source code or standards text that I fetched and read; **[secondary]** = news/blog reporting someone else's facts; **[snippet]** = search-result summary only, page not read in full; **[opinion]** = practitioner argument with no study behind it. Package versions and release dates come from the npm registry queried 2026-10-27. Anything marked "inference" is my reasoning, not a sourced fact. Scope is the notification system itself; undo-vs-confirm evidence belongs to the sibling lane.

## 1. Library prior art: which of the six ideas each library implements, and how

### Takeaway
No library implements idea 1 as stated (extra content of a single toast that expands on hover/tap) and none implements idea 3 as stated (progress that relocates when the user navigates away). Ideas 2 (actions), 4 (per-kind durations, but only per success/error/loading, never per "undo"), and 6 (pause on hover/focus, usually also on window blur or hidden tab) are common. Idea 5 (order by remaining lifetime) appears nowhere; the nearest equivalents are explicit `priority` for ordering or queueing (Mantine, Fluent, Zag) and newest-first stacking. "Expand on hover" in Sonner and Mantine means the stack of toasts fans out, not that one toast reveals more content.

### Cited Findings

**Sonner / vue-sonner** (sonner 2.0.8, npm 2026-08-09; vue-sonner 2.0.9, npm 2025-10-01)
- Defaults: `duration` 4000, `position` bottom-right, `closeButton` false, `dismissible` true, `containerAriaLabel` "Notifications"; Toaster `visibleToasts` 3, `expand` false ("expand on hover"), `gap` 14, `offset` 32px desktop and `mobileOffset` 16px under 600px, `hotkey` Alt/⌥+T. [primary] — [Sonner toast API](https://sonner.emilkowal.ski/toast), [Sonner Toaster API](https://sonner.emilkowal.ski/toaster)
- Actions: `action` is a primary button that runs `onClick` and closes the toast (`event.preventDefault()` keeps it open); `cancel` is a secondary button that closes and runs `onClick`; both accept JSX. `promise` shows loading then updates on resolve or reject; `loading` gives a spinner toast for manual handling; `onDismiss` and `onAutoClose` callbacks exist. [primary] — [Sonner toast API](https://sonner.emilkowal.ski/toast)
- Source (main branch fetched 2026-10-27, package.json 2.0.8): the auto-close timer is paused when `expanded || interacting || isDocumentHidden`, and the remaining time is banked and resumed (not restarted). Loading/promise toasts and `duration: Infinity` never start a timer. [primary] — [sonner src/index.tsx](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx)
- Source: a new toast is prepended (`[toast, ...toasts]`), `isFront = index === 0`, and `isVisible = index + 1 <= visibleToasts`, so the newest toast is the front of the stack and the oldest fall behind and then out of view. Any mouse enter/move over the container sets `expanded`; `mouseleave` collapses unless a swipe/drag is in progress. [primary] — [sonner src/index.tsx](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx)
- Source: swipe dismiss uses a 45 px threshold or a velocity above 0.11 px/ms, and is limited to configured `swipeDirections`; the container is an `aria-live="polite"` region with `aria-relevant="additions text"` and `aria-atomic="false"`, labelled "Notifications <hotkey>". [primary] — [sonner src/index.tsx](https://github.com/emilkowalski/sonner/blob/main/src/index.tsx)
- Author's write-up: toasts are absolutely positioned; each toast's Y offset is index × gap and it scales down by 0.05 × index; stacked toasts take the front toast's height so uneven heights do not poke out; hovering expands the stack with offsets summed from preceding heights; a pseudo-element fills the gaps between toasts so hover is not lost between them; the page-hidden hook pauses timers so toasts do not expire unseen. Publication date was not shown on the fetched page. [primary, author] — [Emil Kowalski, Building a toast component](https://emilkowal.ski/ui/building-a-toast-component)
- vue-sonner README (no version/date on the page): `expand`, `visibleToasts` (default 3), `position` (default top-right), `duration` (`Infinity` keeps on screen), `closeButton`, `richColors`, `offset`, `theme`, `hotkey` default Alt+T, `toast.custom`, `toast.dismiss(id)`, `onDismiss`, `onAutoClose`, `action: { label, onClick }`. It documents no `cancel` option and no `pauseWhenPageIsHidden`. [primary] — [vue-sonner README](https://github.com/xiaoluoboding/vue-sonner)
- Idea map: 1 = stack expands on hover, not per-toast content (partial); 2 = action and cancel; 3 = loading/promise toast only, no navigation behaviour; 4 = per-toast `duration` only; 5 = newest in front, no lifetime sort; 6 = pause on hover/interaction/hidden tab.

**Notivue** (Vue/Nuxt-native, 2.4.5, npm 2024-09-01)
- Defaults from the docs' `defaultConfig`: `pauseOnHover` true, `pauseOnTouch` true, `pauseOnTabChange` true, `enqueue` false, `avoidDuplicates` false, `position` `'top-center'`, `limit` `Infinity`. [primary] — [Notivue configuration](https://docs.notivue.smastrom.io/stream-customization/configuration)
- Per-type defaults: success, error, warning and info are 6000 ms; `promise` is `Infinity`; `promise-resolve` and `promise-reject` are 6000 ms. ARIA per type: success/info/promise `polite` + `role="status"`; warning `polite` + `role="alert"`; error and `promise-reject` `assertive` + `role="alert"`. [primary] — [Notivue configuration](https://docs.notivue.smastrom.io/stream-customization/configuration)
- `limit` caps visible notifications. With `enqueue: false` a new push removes the oldest visible one, which may be dismissed before being read or announced; with `enqueue: true` extras wait and each is displayed and announced when its turn comes. Per-push `skipQueue: true` bypasses the queue. The docs recommend `enqueue: true` with `limit: 1` to follow Material's snackbar guidance. Stack order and ARIA live-region structure are not described on that page. [primary] — [Notivue limit and queue](https://docs.notivue.smastrom.io/stream-customization/limit-and-queue)
- The 2.4.0 release note says that with `pauseOnTabChange` disabled, timers keep running after window blur rather than notifications being destroyed. [snippet] — [Notivue v2.4.0 release](https://github.com/smastrom/notivue/releases/tag/v2.4.0)
- Home page lists: pause on hover, clear on swipe, no duplicates, progress bars, headless mode with actions and promise handling, instance controls (dismiss all, destroy all). Defaults and notification-center behaviour are not on the home page. [primary] — [Notivue](https://notivue.smastrom.io/)
- Idea map: 2 = headless actions; 3 = promise type only; 4 = per-type duration table (but all four non-promise types default to 6000); 6 = pause on hover, touch and tab change.

**vue-toastification** (latest 1.7.14, npm 2021-10-18; `next` tag 2.0.0-rc.5 also 2021-10-18; `dev` 2.0.0-dev.1, 2022-01-31)
- Options and defaults: `timeout` 5000, `pauseOnHover` true, `pauseOnFocusLoss` true, `closeOnClick` true, `draggable` true with `draggablePercent` 0.6, `maxToasts` 20, `newestOnTop` true, `hideProgressBar` false, `accessibility` `{ toastRole: "alert", closeButtonLabel: "close" }`. `toast.update(id, { content, options }, create)`, `toast.dismiss(id)`, `toast.clear()`. No dedicated action-button API; buttons come through custom components. The docs target v2 for Vue 3. [primary] — [vue-toastification README](https://github.com/Maronato/vue-toastification)
- Inference: no stable release since 2021-10-18, so treat it as stale prior art for Vue 3 rather than a live dependency choice.

**Reka UI / Radix Vue / Radix Toast** (reka-ui 2.11.0, npm 2026-10-05; radix-vue last 1.9.17, npm 2025-02-28)
- Radix defaults: Provider `duration` 5000, `swipeDirection` "right", `swipeThreshold` 50; Viewport `hotkey` `["F8"]`, label "Notifications ({hotkey})"; Root `type` "foreground"; events `onPause`, `onResume`, `onSwipeStart/Move/End/Cancel`; `Action` requires `altText`. [primary] — [Radix Toast](https://www.radix-ui.com/primitives/docs/components/toast)
- Radix accessibility text: foreground toasts are announced immediately (results of user actions), background toasts at the next graceful opportunity (background tasks); the fetch summary says the page advises longer durations for toasts with an action (exact wording not confirmed). [primary] — [Radix Toast](https://www.radix-ui.com/primitives/docs/components/toast)
- Reka (the Vue port): `duration` 0 or `Infinity` keeps the toast open and a toast's value overrides Root and Provider; "pauses closing on hover, focus and window blur"; F8 focuses the viewport and Esc closes a focused toast; swipe state is exposed via `data-swipe` and CSS variables; `Action` needs `altText`, and `closeOnClick` defaults true. The Reka page does not list prop defaults; the defaults above are Radix's. [primary] — [Reka UI Toast](https://reka-ui.com/docs/components/toast)
- Idea map: 2 = `Action` with mandatory `altText`; 4 = no preset per kind, but `type` foreground/background controls announcement; 6 = pause on hover, focus and window blur.

**Mantine notifications** (@mantine/notifications 9.7.4, npm 2026-10-25)
- Source defaults: `position` bottom-right, `autoClose` 4000, `limit` 5, `transitionDuration` 250, `pauseResetOnHover` "all", `layout` "default" (the alternative is "stacked"), `withAutoCloseProgress` false. [primary] — [Mantine Notifications.tsx](https://github.com/mantinedev/mantine/blob/master/packages/%40mantine/notifications/src/Notifications.tsx)
- Docs: `priority` (default 0) — higher values display first and a higher-priority item can take a visible slot, pushing the lowest-priority visible one back into the queue (its `onOpen` runs again when it returns); same priority keeps insertion order; without priorities the queue is FIFO. `notifications.update`, `hide`, `clean`, `cleanQueue`, `promise` exist; `loading: true` gives a spinner and a loading notification has `autoClose: false`. `allowClose: false` disables the close button and drag/scroll dismissal. `createNotificationsStore()` and `useNotifications()` expose displayed and queued arrays. [primary] — [Mantine Notifications docs](https://mantine.dev/x/notifications/)
- Docs, stacked layout: the stack expands on mouse hover, keyboard focus or a touch tap, and a tap outside collapses it; while collapsed, older notifications are `inert` (not focusable and hidden from screen readers). [primary] — [Mantine Notifications docs](https://mantine.dev/x/notifications/)
- Source: hover/focus on any notification counts toward a shared "active" counter and is released on unmount so a notification dismissed while hovered cannot leave the stack paused or expanded forever. [primary] — [Mantine NotificationContainer.tsx](https://github.com/mantinedev/mantine/blob/master/packages/%40mantine/notifications/src/NotificationContainer.tsx)
- Inference: the option name ("pause **and reset**") and the effect that re-arms `setTimeout(handleHide, autoCloseDuration)` with the full duration suggest Mantine restarts the full timer after hover rather than resuming the remainder; I did not run it to confirm.
- Idea map: 2 = no first-class action prop in the docs I read (custom `renderNotification`); 3 = `loading` plus `update`; 5 = `priority`; 6 = pause with reset, scope "all" or "notification".

**Ark UI / Zag.js toast** (@zag-js/toast 1.47.0, npm 2026-10-26; @ark-ui/vue 5.39.3, npm 2026-10-05)
- Defaults: `placement` "bottom"; `gap` 16; `offsets` "1rem"; `max` 24 on Ark (queued beyond that); `removeDelay` 200 ms; `overlap` (boolean, no default listed) makes toasts overlap; `pauseOnPageIdle` default false. [primary] — [Ark UI toast](https://ark-ui.com/docs/components/toast)
- Zag docs: default durations by type are info 5000, error 5000, success 2000, loading `Infinity`; timers pause when the user hovers or focuses the region; `toaster.pause(id?)` and `toaster.resume(id?)`; when `max` is reached the queued toasts are sorted by priority (1 highest, 8 lowest); `alt + T` focuses the region (configurable); `toaster.promise` returns `{ id, unwrap }`; `toaster.update(id, …)` accepts an object or a function. The Zag page does not mention `aria-live`, role or Esc. [primary] — [Zag toast](https://zagjs.com/components/react/toast)
- Idea map: 2 = `ActionTrigger` part; 4 = per-type default table; 5 = priority for the queue; 6 = pause on hover/focus, optional page-idle pause.

**Fluent UI React v9 Toast** (@fluentui/react-toast 9.8.5, npm 2026-10-19)
- API report: `Toaster` props `limit`, `position` (`top-end`/`top-start`/`bottom-end`/`bottom-start`/`top`/`bottom`), `timeout`, `pauseOnHover`, `pauseOnWindowBlur`, `offset`, `inline`, `announce`, `shortcuts.focus`; `dispatchToast(content, { intent, priority, politeness, timeout, pauseOnHover, pauseOnWindowBlur, onStatusChange, toastId })`; controller methods `dismissToast`, `dismissAllToasts`, `updateToast`, `pauseToast`, `playToast`. `onStatusChange` reports `queued` / `visible` / `dismissed` / `unmounted`. The report lists no default values and does not define what `priority` orders. [primary] — [react-toast.api.md](https://raw.githubusercontent.com/microsoft/fluentui/master/packages/react-components/react-toast/library/etc/react-toast.api.md)
- Idea map: 4 = per-toast `timeout`; 5 = per-toast `priority` (semantics not verified); 6 = hover and window-blur pause per toast, plus programmatic pause/play.

**MUI Snackbar / Notistack** (notistack 3.0.2, npm 2025-01-18)
- MUI: `autoHideDuration` default `null` (no auto-hide); `onClose` reasons `timeout`, `clickaway`, `escapeKeyDown`; `disableWindowBlurListener` default false (the timer expires even when the window is unfocused if set true); `resumeHideDuration` is the wait after user interaction, falling back to `autoHideDuration / 2`; `action` renders after the message. The page does not say what hover does. [primary] — [MUI Snackbar API](https://mui.com/material-ui/api/snackbar/)
- Notistack: default dismissal 5 s, timer pauses when the tab is blurred and resumes on focus; `maxSnack` (docs cite Material guidance of 1); `persist` (if all visible ones are persistent, the oldest is ignored to make room); `preventDuplicate` (by message, or by `key` when given); `action` per snackbar or provider-wide; `closeSnackbar()` with no argument closes all. [primary] — [Notistack basic features](https://notistack.com/features/basic)
- Idea map: 6 = MUI's `resumeHideDuration` is the only library knob I found that explicitly sets how long the toast lives after interaction, i.e. "extend" rather than "pause".

**React Aria Toast (Adobe)** (marked UNSTABLE_ in the docs)
- Recommends a minimum 5 s timeout; timers pause on focus or hover; only auto-dismiss when the information is not critical or can be found elsewhere; toast regions are landmarks reachable with F6 / Shift+F6; the docs' CSS uses `flex-direction: column-reverse`; the close button should be a sibling of the content so a screen reader reads content first; closing a toast moves focus to the next one, and the last close returns focus to where it was. The page says nothing about page-hidden pausing, `aria-live` or actions guidance. [primary] — [React Aria Toast](https://react-aria.adobe.com/Toast)

**Design-system "flags" and banners**
- Carbon: toasts persist by default but may auto-dismiss "after five seconds"; they stack with new toasts at the top of the list; top-right placement; two lines of text maximum; at most one action; optional timestamp, used consistently. Actionable notifications take focus when triggered ("They disrupt screen readers and keyboard users"); for toasts that can auto-dismiss, users should be able to find the information elsewhere. [primary] — [Carbon notification usage](https://carbondesignsystem.com/components/notification/usage/)
- Atlassian flags: bottom-left; "Never use auto dismiss flags for any critical warning or error messages"; bold flags are not dismissible and stay until resolved or expired (success); maximum two links as actions; most recent flag on top; dismissing one brings older ones forward; never mix dismissible and non-dismissible flags in one stack; flags stay above modals. [primary] — [Atlassian flag usage](https://atlassian.design/components/flag/usage)
- Elastic EUI: default lifetime 10 s with "Users should be able read the message in 6 to 7 seconds"; guidance is to display one toast at a time; `showClearAllButtonAt` defaults to 3 (a "Clear all" button appears at three toasts); toast list `role` defaults to `log`; `alert` only if every toast needs immediate attention. [primary] — [EUI toast](https://eui.elastic.co/next/docs/display/toast)
- Material (Android Components): only one snackbar at a time and a new one dismisses the previous; optional action; swipe-off; `LENGTH_INDEFINITE` until dismissed or replaced; `setAnchorView` lifts it above a FAB or bottom navigation. The numeric Material 3 duration guidance could not be read (page renders client-side). [primary] — [material-components-android Snackbar.md](https://github.com/material-components/material-components-android/blob/master/docs/components/Snackbar.md)
- GOV.UK notification banner: inline, placed immediately before the page `h1`, not a floating toast; success banners use `role="alert"` so focus moves; "Remove a green notification banner when the user moves to a new page"; dismissal is listed as an open research question; no timed disappearance. [primary] — [GOV.UK notification banner](https://design-system.service.gov.uk/components/notification-banner/)

**Other defaults worth knowing**
- react-hot-toast durations: blank 4000, error 4000, success 2000, custom 4000, loading `Infinity`; update by id; `dismiss()` with no id closes all. [primary] — [react-hot-toast API](https://react-hot-toast.com/docs/toast)
- PrimeReact v11 toast pauses on hover, interaction and document visibility; Nuxt UI default timeout 5000 with progress pausing on hover. [snippet] — [PrimeReact toast](https://v11.primereact.org/docs/primitive/toast), [Nuxt UI PR 2661](https://redirect.github.com/nuxt/ui/pull/2661)

### Inferences
- Idea 1 has no library precedent as a toast feature. The nearest precedents are different mechanisms: stack expansion (Sonner, Mantine), and OS notification expansion (iOS long press, section 2). A toast whose body expands is therefore novel design work, and the hover/tap split has to be designed against SC 1.4.13 (section 3) because Mantine's tap-to-expand stack is the only touch-aware prior art found.
- Idea 5 as written (short-lived above long-lived) has no precedent. Everything that orders non-chronologically uses an explicit rank (`priority` in Mantine, Fluent, Zag). Atlassian's warning that dismissing a flag brings older flags forward, "so ordering and priority need deliberate planning", argues that a stack that reorders by remaining lifetime will reshuffle as timers expire; I found no study of reshuffling cost.
- Idea 6 splits into three distinct behaviours across the field: pause then resume remaining time (Sonner, Radix/Reka, Zag, our ToastHost), pause then restart the full timer (Mantine, probably), and wait a different time after interaction (MUI `resumeHideDuration`). A pause scoped to the whole stack (Sonner, Notivue "all", Mantine "all" default, our ToastHost) versus per toast (Mantine `'notification'`, Fluent per-toast `pauseOnHover`, Zag `pause(id)`) is the second axis.
- Pause on window blur / hidden tab is near-universal (Sonner, Radix/Reka, Fluent, Notivue, Notistack, MUI, vue-toastification, PrimeReact; opt-in in Zag). Our ToastHost lacks it (section 6).

### Gaps
- Fluent `priority` semantics and defaults for `timeout` / `pauseOnHover` were not retrievable from the API report; the Storybook docs are client-rendered.
- Notivue's stack order, `aria-live` container structure and notification-center behaviour were not on the pages read; its 2.4.0 note is a search snippet only.
- Mantine's default for `withCloseButton` and any `aria-live` use were not found; Mantine's reset-versus-resume behaviour was not tested.
- vue-sonner's `pauseWhenPageIsHidden` is not in the README; whether it inherits Sonner's hidden-tab pause was not checked in its source.
- Material 3 numeric snackbar duration guidance (the figure of 4 to 10 seconds that I recall) was not verified, because m3.material.io returned an empty shell; Material Components Android only documents the constants without values.
- No usability study comparing hover-pause variants (resume vs restart) was found.

## 2. Product patterns for pinned progress and the notification centre

### Takeaway
Platforms handle long-running work with a persistent, updatable single item that survives navigation and can be dismissed, plus a final replacement at completion: Windows updates a progress notification in place by tag and replaces it when done; Android requires a visible ongoing notification for foreground services and now has a progress-centric style; iOS Live Activities are one updating item with an end state and a lock-screen linger of up to 4 hours. In-app guidance from VS Code goes the other way for toasts: keep progress in context and treat a progress notification as a last resort. The "moves to a notification bar when you navigate away" behaviour in idea 3 is closest to the Windows toast-to-Action-Center model and Chrome's download bubble, but I found no web UI library that implements it.

### Cited Findings
- Windows app notifications: a progress bar can be determinate or indeterminate and is updated by data binding using a Tag (and optional Group) with a sequence number, "without re-sending the entire notification". Updating keeps the item's position in Notification Center and does not re-pop a banner; if the user dismissed it, the update fails. For the end state, the docs advise replacing the notification, because the final layout differs and the user may have dismissed the progress item but still wants to know it finished. The page is dated 2025-07-28, updated 2026-04-21. [primary] — [Microsoft Learn, App notification progress bar](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-progress-bar)
- Android foreground services: the system requires a status-bar notification for them; since Android 13 (API 33) users can dismiss it by default and `setOngoing(true)` makes it non-dismissible; on Android 12+ the system waits 10 seconds before showing it, except for cases such as notifications with action buttons. [primary, via search excerpt] — [Android foreground services](https://developer.android.com/guide/components/foreground-services)
- Android 16 (API 36) adds `Notification.ProgressStyle` "to help users seamlessly track user-initiated, start-to-end journeys" (rideshare, delivery, navigation), with segments, points and a tracker icon, and the guidance to "Update the progress experience frequently and accurately". Shown on the lock screen and notification shade. Page updated 2026-03-03. [primary] — [Android 16 progress-centric notifications](https://developer.android.com/about/versions/16/features/progress-centric-notifications)
- iOS Live Activities, per a mirror of Apple's HIG: for tasks with a clear start and end; do not offer one for anything over eight hours; end it as soon as the task finishes; update only when content changes; for several events cycle one activity rather than starting new ones; alert only when truly needed; the Dynamic Island removes an ended activity immediately and the Lock Screen keeps it up to four hours (a 15 to 30 minute custom removal time is suggested). Compact is used for one activity, minimal when several are active, expanded on touch-and-hold. [secondary, mirror of HIG; Apple's page itself could not be fetched] — [apple-hig-mcp live-activities.md](https://unpkg.com/apple-hig-mcp@1.1.3/content/platforms/ios/live-activities.md)
- VS Code notification UX: limit notifications "to respect the user's attention"; show one at a time; combine several into one; low-priority progress belongs in the status bar; a progress notification "should be used as a last resort" because "progress is best kept within context"; do give a details link, update the message as work proceeds, offer cancel where it applies, and never leave a progress notification running indefinitely; add "Do not show again". [primary] — [VS Code notifications UX](https://code.visualstudio.com/api/ux-guidelines/notifications)
- Chrome's download bubble replaced the bottom download shelf with a toolbar icon; early patch notes describe a ring that fills with progress and an icon shown while downloads are in progress or were started within the last 24 hours. [secondary/snippet, news coverage of Chromium patch notes; no Chromium primary found] — [TechRadar](https://www.techradar.com/news/google-chromes-downloads-bar-is-getting-less-annoying), [Android Police](https://www.androidpolice.com/chrome-new-download-ui-progress-bars/)
- Google Drive on Android shows a bottom sheet above the bottom bar with the count of uploading items and estimated time left; its chevron opens an Uploads page listing all pending or recently completed uploads. This is the Android app; I could not confirm the web-app upload panel's behaviour across navigation. [secondary/snippet] — [9to5Google](https://9to5google.com/?p=677681)
- Notification centre versus toast: sources I found agree that a toast should not be the only place a message lives; a centre holds what the user may need to revisit, act on or audit. The strongest statement is a vendor blog (Courier sells notification infrastructure) that a toast cannot be the only place to read an error or to offer an Undo action. [opinion/snippet, vendor-authored] — [Courier](https://www.courier.com/blog/youre-not-github-toasts-are-probably-fine-for-your-app), [saasui.design](https://www.saasui.design/blog/saas-notification-toast-ux-patterns)
- Adam Silver (15 March 2020) recommends for constant feedback such as save status a persistent status area that can be checked at a glance and clicked for history, like Google Docs' header status. [opinion] — [Adam Silver](https://adamsilver.io/blog/the-problem-with-snackbars-and-toast-messages/)
- WCAG 2.2.2 Pause, Stop, Hide (Level A): auto-updating information that starts automatically and is presented in parallel with other content needs a mechanism to pause, stop or hide it or control the update frequency; there is no 5-second exemption for auto-updating content. A preloader that is the only content on the page is exempt, and Note 4 says a preload animation can count as essential if omitting progress would make the user think the page is broken. [primary] — [WCAG 2.2 Understanding 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
- WCAG 4.1.3 Status Messages (Level AA): a status message includes "the progress of a process"; progress must be programmatically determinable (for example `role="status"`) without taking focus, and the Understanding page warns that over-using live regions makes an app too "chatty". [primary] — [WCAG 2.2 Understanding 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- Atlassian's rule "Never use dismissible and non-dismissible flags in a stack" is directly relevant to mixing a pinned (non-dismissible) item with transient ones. [primary] — [Atlassian flag usage](https://atlassian.design/components/flag/usage)
- Windows (Tag and Group) and Live Activities (one activity instance, updated in place) both treat the progress item as one object updated by identity. Our bus already has stable ids and in-place update (section 6).

### Inferences
- Idea 3's "hide" button maps to SC 2.2.2's "pause, stop or hide" requirement, so it is not optional if the progress updates automatically beside other content.
- A hidden pinned item should keep running and remain recoverable from a list, as the Windows model (dismiss means updates fail, so show a replacement at completion) and the Live Activity model imply; otherwise "hide" silently loses the completion outcome.
- Relocating on navigation is simple for SPA route changes because the bus and ToastHost are module-level state, but it does nothing for full page loads or tab close; surviving those needs persistence, and for uploads the owning queue must outlive the route. In our SDK `UploadQueue.spec.md` says "The owned Vue queue cancels its remaining uploads on scope disposal" (section 6), so a route-scoped queue would cancel on navigation.
- VS Code's guidance (progress in context first, notification last) matches the developer's idea: page shows progress inline while the user is on it, and the notification form is the fallback after navigation. Idea 3 is consistent with that hierarchy; the open design question is the second surface (bell list versus top pop-up). The iOS model (one item cycling through events) argues for one aggregated pinned entry instead of N progress rows when several jobs run.

### Gaps
- Primary sources for Chrome's download bubble and for Google Drive's web upload panel were not found; both rest on news coverage or the Android app.
- Apple's HIG page for Live Activities could not be fetched; the rules above are from a third-party mirror. The eight-hour figure should be confirmed on Apple's page.
- Vercel and GitHub Actions deploy-status UIs, Linear and Slack activity inboxes were not researched in this pass (I did not search for them), so no claims are made about them.
- No library or design-system page was found that specifies a "toast becomes list entry on navigation" behaviour.

## 3. Timing guidance and what WCAG requires of auto-dismissing toasts

### Takeaway
Published defaults cluster at 4 to 6 seconds for plain toasts, with 5 s the most common floor and 6 s the explicit accessibility minimum in Adobe Spectrum and Dialpad Dialtone; error or actionable toasts are treated as persistent or longer in Carbon, Atlassian, React Aria and Radix. No source gives a defensible reading-time formula: the one published per-word rule (Spectrum's +1000 ms per 120 words) is far slower than measured reading speed would justify, and Gmail's configurable 5, 10, 20 or 30 second Undo Send window is the one per-user undo timing control I found in a widely deployed product. WCAG does not forbid auto-dismissal but SC 2.2.1 bites when the toast is the only way to reach the information or action, which is exactly the Undo case.

### Inferences
- Pause on hover/focus is not one of the three ways 2.2.1 lists (turn off, adjust 10x, extend with a 20 s warning), so by itself it does not satisfy the criterion for a toast that is the only route to an action. For Undo the likely compliant route is a user-adjustable undo window (Gmail's 5 to 30 s is a 6x range, below the criterion's tenfold wording) or no timer with an alternate route such as a history list. Whether an undo window is an "essential" limit is a judgement call the W3C thread did not settle.
- A reading-time floor derived from Brysbaert's 238 wpm is about 4 words per second, so a 10-word message costs roughly 2.5 s of pure reading before reaction time; the common 5 to 6 s floors therefore cover roughly 20 to 24 words, and a toast of 40 words would need about 10 s at average speed. Spectrum's +1 s per 120 words is far below that rate and looks inconsistent with measured reading speed. A candidate rule would be `max(floor, reaction + words / 4 + (action ? extra : 0))`, with the constants chosen by us; none of those constants is sourced.
- Because `danger` already gets 8 s in our SDK, adding a kind-based table (undo longer than plain) matches how Notivue, Zag, react-hot-toast and our own `DefaultToastDurations` already work; the novelty is only that "undo" is a capability of the toast (it has a revert action) rather than a severity.
- Mapping notification types to politeness (alert for errors, status for others) is expected by 4.1.3 and by Notivue/Radix/Fluent; our single polite announce region does not do this (section 6).

## 4. Stacking and placement: order, maximum visible, collapsed stacks, placement, interference

### Takeaway
The dominant convention is newest-first at the edge of the stack (Sonner, Carbon, Atlassian, vue-toastification default), with a small visible cap (Sonner 3, Mantine 5, ours 5) and the rest queued; Material, EUI and Notivue's own docs go further and recommend one at a time. Collapsed "fan" stacks are an optional presentation (Sonner, Mantine `stacked`, Zag `overlap`) that expand on hover, and Mantine alone documents the touch and keyboard equivalents and makes hidden items `inert`. Placement defaults vary (top-right, bottom-right, bottom-center, bottom-left); only Material, Spectrum and Sonner's mobile offset address bottom navigation and floating buttons. I found no usability study on stack order or placement.

## 5. Undo mechanics: deferred commit versus compensating action, navigation, batching, limits

### Takeaway
Two implementation strategies exist. Deferred commit hides the item and runs the real operation after the undo window, so Undo just cancels a timer; it avoids server-side revert logic but loses the operation if the page goes away mid-window and is unreliable to flush on unload. Compensating action performs the operation at once and Undo issues a reverse operation or restores a soft-deleted record; it survives navigation and tab close but needs a restore path and can race with other effects. The foundational guidance dates from 2007 and says to prefer undo to confirmation where the action is reversible; it explicitly does not cover irreversible actions such as sending email.

### Cited Findings
- Aza Raskin, "Never Use a Warning When you Mean Undo" (A List Apart, 21 July 2007): users build a habit of clicking OK, so louder warnings do not help; let the action proceed and offer a way to reverse it; the examples are Gmail's undo after delete plus trash recovery, Google Calendar's warning without undo, and Highrise warnings. The article does not address irreversible actions such as sending email; comments proposed soft-delete flags purged later, deferring the action until the next command, a delayed-send feature (others noted that delays frustrate time-sensitive senders), and noted difficulty with undo in shared multi-user documents. Older than the 2022 preference, kept as the canonical source. [primary, 2007] — [A List Apart](https://alistapart.com/article/neveruseawarning/)
- Practitioner descriptions of the two strategies: remove the row optimistically, show an Undo toast for about five seconds, cancel the pending delete on Undo and call the delete API only after the timeout (deferred); or send the delete immediately and issue a restore on Undo (compensating, which needs a viable reverse operation). One article argues deletes, account closures, cancellations, transfers and payments suit a pessimistic UI that waits for the server instead. [opinion/snippet] — [dev.to: pessimistic UI for destructive actions](https://dev.to/137foundry/why-pessimistic-ui-is-still-the-right-call-for-destructive-actions-447j), [dev.to: useOptimistic patterns](https://dev.to/stacknotice/react-useoptimistic-optimistic-ui-patterns-that-actually-work-2026-5460)
- Page lifecycle: MDN says `beforeunload` "is not reliably fired, especially on mobile platforms" (for example when a mobile user switches apps and later closes the browser); `visibilitychange` "provides a more reliable signal for when to save the application state"; modern browsers show only a generic prompt, require sticky user activation before showing it, and the listener should be added only while there are unsaved changes. [primary] — [MDN: beforeunload](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)
- Gmail's Undo Send: a configurable window of 5, 10, 20 or 30 seconds after sending; the page does not say what happens on tab close. [primary] — [Gmail Help](https://support.google.com/mail/answer/1284885)
- Material Android: one snackbar at a time, and showing a new one dismisses the previous; an action click dismisses the snackbar. — [Material Snackbar.md](https://github.com/material-components/material-components-android/blob/master/docs/components/Snackbar.md)
- Keyboard reach: Silver says snackbar actions are far in the tab order and may vanish before a keyboard user arrives; Carbon says actionable notifications take focus ("They disrupt screen readers and keyboard users"); React Aria returns focus to the prior element when the last toast closes; Radix, Sonner, Zag and Fluent provide a hotkey to jump to the toast region. [opinion/primary] — [Adam Silver](https://adamsilver.io/blog/the-problem-with-snackbars-and-toast-messages/), [Carbon](https://carbondesignsystem.com/components/notification/usage/), [React Aria Toast](https://react-aria.adobe.com/Toast)
- Reuse of one notification for repeated operations: Sonner/Mantine/Zag/Fluent/vue-toastification all support update by id; Notistack and Notivue support de-duplication by key or message. This is the mechanism for "3 items deleted, Undo" batches. — respective sources in section 1
- Per Courier's blog, Undo should not exist only in a toast; per Silver the toast's disappearance after about five seconds is the failure mode. [opinion] — [Courier](https://www.courier.com/blog/youre-not-github-toasts-are-probably-fine-for-your-app), [Adam Silver](https://adamsilver.io/blog/the-problem-with-snackbars-and-toast-messages/)

### Inferences
- For deferred commit, the unload decision is a product decision, not a technical one: either commit on `visibilitychange` hidden (leaving counts as accepting) or drop (leaving counts as cancelling). Since `beforeunload` is unreliable on mobile per MDN, any flush has to hang off `visibilitychange`/`pagehide`, and delivering a request during unload (via `fetch` with `keepalive` or `navigator.sendBeacon`) is something I know exists but did not find in a fetched source, so verify before relying on it.
- SPA route changes do not unload the page; the risk there is that the undo callback closes over a component that unmounts. A module-level owner for the pending operation (the bus already is module state) avoids that.
- Batch undo: coalesce rapid same-kind operations into one notification updated in place (count + a single Undo that reverts the whole batch), because a one-at-a-time rule (Material, Notivue's recommended `limit: 1`) would otherwise make the first operation's Undo unreachable. Whether the earlier pending commit should flush when a new one replaces it is undecided in the sources.
- Undo is a poor fit when the effect leaves the system during the window (emails, payments, webhooks) or the data is shared and edited concurrently (Raskin's commenters); Gmail resolves send by delaying it on purpose.
- Because a pinned alternative surface exists (history list or notification centre), undo that survives the toast's disappearance becomes possible for compensating-action designs; deferred-commit designs can only offer it for as long as the pending state exists.
- A keyboard path for Undo (a shortcut active while the notification is visible) closes the focus/tab-order gap Silver describes; the SDK has shortcut and history foundations that could host it (section 6).

### Gaps
- No source describes tab-close semantics for any production undo toast (Gmail's page is silent); `pagehide` and `keepalive`/`sendBeacon` behaviour was not in the MDN page I read.
- No source compares deferred commit and compensating action in terms of failure rates.
- Batch-undo conventions in Gmail, Drive or Linear were not found.
- Sibling lane covers undo versus confirm; no attempt was made here to cover when a confirmation dialog remains necessary.

## 6. Internal current state (read-only): what `notify` and the toast components support today

### Takeaway

### Inferences
- The six ideas are an extension of an already mature host, not a rewrite. Ideas 2 (actions) and 6 are mostly present. Idea 4 is a table keyed by severity today, so an undo/kind dimension needs a new key (for example a `kind` or "has revert" flag on `FeedbackNotice`), because `tone` expresses severity only.
- `FeedbackToastHost` is the choke point: new fields on `FeedbackNotice` do nothing until `toToastOptions` forwards them, and `category` is currently read in the `subscribe` callback but not in `toToastOptions`.
- The two-surface split (bus + `UndoBar`) and the two unrelated `notify` functions are friction for a unified notifications vector and for the gallery; both are naming and ownership decisions rather than gaps in capability.
- For pinned progress, the bus's retained list plus `NotificationCenterGroup` already provide the "moves to a list" half; what is missing is a notice that updates its content over time (the toast store can `update`, the bus republishes by id, so this is feasible) and an owner that outlives a route for uploads.
- Idea 5 would touch the plain FIFO `slice(0, max)` at `ToastHost.vue:480`, the same place that decides which toasts are visible and whose timers run.

### Gaps
- The consumer usage of `notify` across the "~35 apps" was out of scope (SDK files only), so the actual mix of durations, actions and confirm dialogs in use is unknown.
- I did not run the SDK tests or the gallery, so behaviour claims come from reading code and specs, including the untested live-region inference above.
- The playground fixture `apps/playground/src/gallery/fixtures/FeedbackExamples.ts` only smoke-renders toast components (`smokeCase`); whether a gallery page with interactive toast demos exists was not checked.

## 7. Feature matrix

### Takeaway
Pause on hover is common, actions are common, per-kind default durations are fairly common (Notivue, Zag, react-hot-toast, our SDK); extras that cluster across the best libraries are pause-on-hidden-tab, swipe dismiss, a hotkey to focus the region, update-by-id, promise toasts and a priority or queue. Expandable toast content, kind-aware stacking by lifetime and cross-navigation pinned progress are unoccupied by libraries. Cells use supported / partial / no, with "n/v" where the page I read did not say.

### Inferences
- The matrix has no library with a supported mark in rows 1, 3 and 5 together; those three ideas are original design work for the SDK, and the gallery demos for them cannot be modelled on a library demo.
- Where a library column is "n/v", the cell reflects what I read, not a statement that the feature is absent. The best-covered columns (Sonner source, Notivue config, Mantine source and docs, Fluent API report, Zag docs) are reliable; the Carbon, Atlassian and EUI "n/v" cells in hover and swipe rows reflect that those pages are usage guidelines, not APIs.
- Strong extras for our vector, counted by library columns marked supported in the second table (12 columns): hidden-tab/window-blur pause 6 (plus 1 opt-in), swipe 6, region hotkey 5, update by id 5 (plus our SDK), promise/loading 4 (plus our SDK), per-type politeness 3, inert hidden stacked items 1.

### Gaps
- Several library cells could not be verified from docs (marked n/v); verifying them would need reading source or running demos.
- Product cells for Gmail, Chrome and Drive rest on support pages and news coverage; no source for hover behaviour of those UIs was found.
- The matrix has no row for "Idea 1 on touch" for any OS-level analogue other than iOS long press, which is a search snippet [snippet] — [Apple Developer Forums thread](https://developer.apple.com/forums/thread/800174), [9to5Mac](https://9to5mac.com/2018/11/08/iphone-xr-expand-notifications-haptic-touch/).
